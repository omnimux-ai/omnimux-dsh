# 规格 · 渠道×素材类型（模态）契约矩阵门禁（Issue #3236）

## 背景与目标

真实故障：路由声明（`cordis.patch.yml` 的 `llm-pi-ai` 模型行 `input[]`）只声明 `[text, image]`，而契约派生的 `CHAT_MODELS` 却带 `video/audio/document`。运行期判定读的是契约派生表，于是门禁放行、请求打到上游才被拒（`omnimux-invalid-request` + `does not accept video input`）。

目标：把「路由声明 ↔ 模型契约」的**双向**模态对账做成合入前门禁，覆盖全部模态，并真正进 CI。

## 验收标准

| # | 场景 | 期望 |
| --- | --- | --- |
| M1 | 路由声明的模态 ⊃ 契约声明的模态 | 失败（契约比路由宽松 = 会放行但上游拒绝），列出差异 |
| M2 | 路由声明的模态 ⊂ 契约声明的模态 | 失败（契约过严 = 能力被无谓隐藏），列出差异 |
| M3 | 两侧完全一致 | 通过 |
| M4 | 路由行**没有** `input` 键 | 等价为 `['text']`，不得产生假阳性 |
| M5 | 合成夹具：给 `gemini-3.8-flash` 补上 `video` 声明 | 断言转红（反向对照，证明门禁非恒真） |
| M6 | 当前主干真实数据 | 必须报出预期缺口：`gemini-3.8-flash × {video,audio,document}`、`gemini-3.7-flash × video` |
| M7 | 门禁脚本自身 | 登记进治理清单的 **ciRequired**（非 manual），且挂在 CI 实际执行的命令下 |

## 硬性约束

- 断言必须建立在**两份独立声明**的交叉对账上，禁止任一侧自证（不得只读契约派生投影）。
- 官方渠道组在仓内**没有**模态真源（分组只带 `parameters`）——本期**不得**为官方分组编造模态声明；只做登记表完备性断言（有则校验、无则不要求）。
- 反向对照必须有：合成夹具转红，否则视为恒真门禁。
- 不得为了让门禁变绿而放宽断言；预期缺口以显式清单形式呈现，由后续任务修复。

## 证据要求

- 单测：M1–M5 全部覆盖，含 M5 的反向对照。
- 门禁实跑：在主干真实数据上运行，粘贴 M6 的缺口清单输出。
- CI 挂点核验：证明该命令确实出现在 CI 工作流实际执行的步骤中。
