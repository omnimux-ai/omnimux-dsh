# 中枢媒体链路结构化落盘记录（#3232）

## 背景与问题

中枢媒体链路（`plugins/omnimux/src/media/`）在失败时**不写任何日志文件**，只更新状态账本 `$DSH_HOME/omnimux/media-tasks/`。链路中唯一的运行期痕迹是三处控制台打印（`direct-http.js:240`、`:251`、`execute.js:914`），在打包后的桌面端没有落点。

后果：用户报「生成失败」时，本机拿不到现场，只能靠人工复现。审计（2026-10-07）确认官方 DSH 不提供通用文件 sink——运行期日志默认只到 stdout、不落盘，官方明示桌面端持续日志为未实现项。因此必须自建。

同时确认：现有串联键不足以标识「一次用户操作」——`taskRef` 每次提交新建、重试即换号；`requestKey` 缺省时由服务端合成随机值，且画布与头像提交路径根本不带。本任务不扩到跨插件透传，只保证中枢自身记录完整。

## 用户关键操作旅程

1. 用户在画布、头像或查看器等入口提交一次媒体生成。
2. 提交、轮询、下载各阶段若发生失败，本机留下结构化记录。
3. 出问题后，支持方可在 `$DSH_HOME/omnimux/media-logs/` 找到按日期分文件的记录，按任务编号定位到具体一次操作。
4. 记录文件不会无限增长：单文件超阈值时自动切分。

## 可测验收标准

- A1 记录路径与命名符合 `$DSH_HOME/omnimux/media-logs/media-<YYYY-MM-DD>.ndjson`。
- A2 每条记录是单行合法 JSON，含 `ts`、`event`、`taskRef` 必填字段。
- A3 事件覆盖至少 8 类：入参拒绝、账本短路、提交失败、轮询超时、未知任务、终态失败、下载失败、取回失败。
- A4 单文件超 5 MB 时，后续记录写入带序号后缀的新文件，旧文件保持可读。
- A5 写入失败（目录不可写、磁盘满）时生成主流程行为不变，且不抛出、不影响原始错误。
- A6 记录不含密钥：`authorization`、`apiKey`、`token` 一类字段被脱敏或丢弃。
- A7 并发提交时每条记录独占一行，不出现半行交错。
- A8 单行长度上限 4 KB，超长内容截断并标记。

## 非目标

- 不改状态账本 `$DSH_HOME/omnimux/media-tasks/` 的语义与格式。
- 不做全局 logger 重构，不收敛既有控制台调用（本任务只替换链路上那 3 处）。
- 不做前端错误上报。
- 不补跨插件 `opId` 透传（画布与头像提交路径保持现状）。
- 不做日志删除或保留上限，只做切分。

## 新用户基线

- 依赖：`$DSH_HOME` 下产品自建的存储目录。产品基线（`docs/contracts/product-baseline.md:24-29`、`:42-47`）明确这类目录在新用户机器上确定存在，因此可默认开启，不需要用户开关。
- 缺失或不可写时：目录按需创建；创建或写入失败一律静默降级，生成主流程不受影响，也不吞掉原始错误。

## 已知限制

上游 HTTP 客户端位于外部依赖包 `aigc-provider-runtime-kit` 内，仓内无可挂钩的请求函数，因此记录只能到「提交层」，拿不到更细的线级重试轨迹。
