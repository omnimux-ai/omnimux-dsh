# 规格 · 灵感卡片封面不可渲染时回退视频首帧预览（Issue #2073）

## 问题陈述

灵感社区（灵感库）中，一条导入已成功的 TikTok 灵感（本地视频存在且可播放、详情弹窗正常播放）在网格卡片上显示为「空占位」：居中的播放三角图标 + 标题，没有任何画面。用户因此无法在卡片层面判断素材内容，也无法像其他卡片一样获得可预览的封面。

### 根因（已用生产数据与字节证据确认）

1. 该类记录的封面在导入时被下载并落盘，但扩展名取自 `detectExt(url, '.mp4')` 的**默认值** `.mp4`（TikTok 封面 URL 无可识别后缀），而其真实字节是 ISO-BMFF `ftypheic`（HEIC 图片）。证据：`cover_10b758f2.mp4`，7714 字节，首 8 字节 `00 00 00 1c 66 74 79 70 68 65 69 63`。
2. 本地媒体路由按**扩展名**决定 `Content-Type`（`MEDIA_TYPES`），因此该封面以 `video/mp4` 提供。
3. 卡片只渲染 `<img src={cover_url}>`；加载/解码失败即 `onError` → `broken=true` → 渲染死占位块。详情弹窗走 `<video src={media_urls[0]}>`，所以不受影响。

## 用户旅程（本次验收对象）

1. 用户在灵感社区导入一条 TikTok 链接，导入成功、落入本地库（弹窗可播放）。
2. 用户回到网格视图，看到该卡片的封面区域。
3. **期望**：卡片显示该视频的真实画面（首帧预览），而不是空白占位；悬停出现播放三角与「详情 / 立即复刻」CTA 的行为不变。
4. 用户点击卡片任意位置或「详情」，弹窗行为保持现状（可播放视频）。
5. 用户重新导入一条封面正常（JPEG/PNG/WebP）的链接：卡片封面照旧用封面图渲染，不因本次改动而改变。

## 验收标准（可测）

### AC1 卡片封面回退到视频首帧
- 当 `pickCoverSrc(row)` 为空，或封面 `<img>` 触发 `onError`（404/不可解码）时，只要 `pickVideoSrc(row)` 非空，卡片必须挂载一个 `<video>` 作为封面层：`muted`、`playsInline`、`preload="metadata"`、无控件、不自动播放，并使用与封面图一致的填满裁切与圆角。
- 该 `<video>` 层必须在真实浏览器中产出**正几何尺寸**（`width > 0 && height > 0`）并触发首帧就绪（`loadeddata` 或等价信号），据此隐藏骨架扫光。
- 占位块（播放三角 + 标题）只在「既无可用封面、也无可用视频」时出现。
- 既有行为不得回归：多选复选框、导入中/失败胶囊与失败原因文案、悬停浮层 CTA、`isUsableCoverSize` 对 1×1 占位图的拒绝、懒加载。

### AC2 导入管线不再产出不可渲染的封面
- 封面落盘后必须按**真实字节**校正扩展名（jpeg/png/webp/gif/avif/heic/mp4/webm 等由魔数判定）；不得因 URL 无后缀而盲用 `.mp4`。
- 落盘封面被**确认为**不可渲染载荷（HEIC 静图、视频容器等）时：`cover_url` 必须为空字符串，不得退回到远端原始封面 URL，且该文件不得留在封面目录中。
- 无法被嗅探识别的载荷保持既有行为（仍写 `cover_url`）：拒绝未识别的载荷会误伤正常封面，最小改动优先。
- 封面下载失败（无本地封面）时的既有行为保持：仍可回退到远端 `meta.cover_url`。

### AC3 历史脏数据自愈
- 已入库的脏行（`cover_url` 指向 HEIC 字节的 `.mp4` 文件）无需重新导入：仅凭 AC1 即可在网格中显示视频首帧预览。

## 非目标
- 不引入图像转码依赖（不做 HEIC→JPEG 转码、不引入 ffmpeg/sips）。
- 不改动视频下载与落盘策略、分享/发布契约、Rival 模块与云端目录。
- 不做数据迁移或批量清洗历史文件。

## 验证方式
- 单元测试：卡片渲染（jsdom）、封面扩展名嗅探、导入落盘守卫（HEIC 不写 `cover_url` 且不留文件；无后缀 JPEG 校正为 `.jpg`）。
- 真实浏览器 E2E：本工作树内以 ego-browser 构建真实 Chromium 场景，断言「坏封面 + 有本地视频 → 视频封面层正几何 + 首帧就绪」「无封面无视频 → 占位块」「正常封面 → `<img>` 渲染」，并截图留存证据。
