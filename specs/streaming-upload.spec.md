# 本地大文件直传流式推流规格说明 (Issue #2179)

## 1. 业务背景与问题痛点
当前素材上传链路在处理本地文件时，会通过 `readFile` 一次性将整个文件读取至内存中（Buffer），再通过 Blob 发送请求：
- **起步延迟大**：需等待磁盘把几十上百兆完整加载入内存，首包起步存在卡顿等待；
- **内存消耗高**：百兆视频直接吃掉百兆内存，并发上传容易造成内存暴涨与卡顿风险。

上游网关现已支持直接获取 R2 的预签名 PUT 地址，R2 支持标准流式数据直接写入，客户端无需将大文件完全读进内存，即可实现“边读边推”。

## 2. 详细技术方案设计

### 2.1 轻量元数据探测 (Lazy Metadata)
- 在解析本地文件时，仅通过 `stat` 读取文件大小、修改时间与基本文件属性；
- 文件 MIME 类型优先通过扩展名映射表解析（覆盖 99% 的常见图片与视频扩展名）；若扩展名未知，仅读取头部前 512 字节魔数（Magic Number），绝不预读全量文件内容；
- 返回文件描述对象，包含按需创建数据流的能力：`createStream: () => Readable.toWeb(createReadStream(filePath))`。

### 2.2 R2 预签名直传数据流直推 (Streaming Direct Upload)
- 在 `uploadDirectToStorage` 中，若素材来源支持流式传输（存在 `createStream` 且体积大于阈值或为普通物理文件）：
  - 直接调用 `createStream()` 获取标准 `ReadableStream`；
  - 在 `fetcher` 发起 HTTP PUT 请求时，配置 `duplex: 'half'` 与 `Content-Length: fileStat.size`；
  - 数据以块（Chunk）为单位平滑从磁盘流向云端存储，内存占用稳定在几十 KB，首包起步零等待。

### 2.3 容灾与中转降级保障 (Fallback Compatibility)
- 对于小图、dataURI 等非文件型素材，依然保持原有内存载荷模式自适应处理；
- 若网关不支持直传（501/404）需要回退至中转通道 `uploadViaGateway` 时，按需回落，保障 100% 成功率。

## 3. 验收标准 (Acceptance Criteria)
- [ ] **AC-1 (流式直传)**：物理文件直传时，通过数据流（Web Stream / `duplex: 'half'`）直推存储，不调用 `readFile` 全包读入；
- [ ] **AC-2 (内存开销)**：大文件上传时内存开销不随文件大小成倍增长；
- [ ] **AC-3 (轻量元数据探测)**：常见扩展名文件无需读取全量内容即可解析出正确的 MIME 类型与文件大小；
- [ ] **AC-4 (中转与回退兼任)**：直传失败或非物理文件场景下回退中转逻辑保持完整可用；
- [ ] **AC-5 (全量回归)**：自动化测试 100% 通过。
