# 规格说明：质量门禁硬化（任务级规格校验 + 端到端完整性 + 关闭 bash 绕过）

**文件：** `specs/quality-gate-hardening.spec.md` ｜ **优先级：** P0

## 1. 事故与根因

首个版本的质量门禁（`scripts/guard-quality-loop.mjs`）上线后，在「修复内容遮挡 Tab 选项卡」任务（PR #1628 / `323b24b33`）中**一次都没有拦截**。经取证确认（`~/.dsh/logs/dsh-hooks/dsh-hooks.log`：该门禁共执行 67 次，67 次全部 `allow`，0 次 `deny`），根因有四项：

1. **规格校验非任务级（致命）**：`hasValidSpec()` 只检查 `specs/` 目录下**是否存在任意一个** ≥50 字符的 `.md`。仓库已有 8 份规格文档，因此该条件**永久为真**，门禁退化为空转。实测：在主干对任意业务源码发起编辑，门禁直接放行。
2. **验证证据校验非任务级（致命）**：`hasVerifyEvidence()` 只检查 `.workbuddy/evidence/` 目录**是否存在任意文件**。该目录已有 109 项历史证据，同样**永久为真**。
3. **缺少端到端完整性门禁**：原设计只拦截「写入端到端测试文件」这一动作，**从不要求端到端测试必须存在**。智能体写一条自查源码字符串的单元测试即可绕过，端到端测试永远可以缺失。
4. **bash 绕过**：门禁在 `.dsh/hooks.json` 中的匹配器仅为 `edit|write`。通过终端命令（重定向、脚本写入、就地替换）改源码完全不经过该门禁。

## 2. 修复设计

### 2.1 门禁一：任务级规格校验（Spec Gate，任务级）
- **触发**：`edit` / `write` 目标为业务源码；以及 `bash` 命令疑似写入业务源码。
- **判定**：规格必须**属于当前任务**，即满足以下任一条：
  - 在未提交改动（`git status --porcelain`）中出现新增或修改的 `specs/*.md`；
  - 在相对 `origin/main` 的领先提交中出现新增或修改的 `specs/*.md`。
- **否则**：`deny`。
- **豁免**：`specs/**`、纯文档、测试脚本、配置、脚本目录、临时目录与工作树外路径。

### 2.2 门禁二：验证证据时效校验（Verify Gate，任务级）
- **触发**：创建或修改端到端/UI 自动化测试脚本。
- **判定**：存在**本任务窗口内**（默认 4 小时）新产生或被修改的验证证据（`.workbuddy/evidence/**`、`tmp/**` 下的截图或报告、工作树内同类产物）。
- **否则**：`deny`。

### 2.3 门禁三：端到端完整性门禁（Test Completeness Gate，新增）
- **触发**：`git commit`、`git push`、`gh pr create`、`gh pr merge`。
- **判定**：若当前任务改动集合（未提交改动 ∪ 相对 `origin/main` 的领先提交）中**包含界面/客户端源码改动**，则改动集合中**必须同时包含端到端测试文件**。
- **界面/客户端源码**判定：路径位于 `*/src/client/**`、`*/extension/src/**`、`*/client/**`，或后缀为 `.css`、`.tsx`、`.jsx`。
- **端到端测试文件**判定：路径含 `/tests/e2e/`、`/e2e/`，或文件名含 `.e2e.test.`，或位于测试目录且后缀为 `.spec.ts` / `.spec.js`。
- **否则**：`deny`，并输出补齐指引。

### 2.4 关闭 bash 绕过
- 门禁匹配器扩展为 `edit|write|bash`。
- `bash` 命令按「疑似写入业务源码」识别：重定向（`>`、`>>`）、`tee`、`sed -i`、`python -c`/`node -e` 且命令体出现 `open(` 写模式或 `writeFileSync`、`cp`/`mv` 指向业务源码路径。
- 命中后与 `edit`/`write` 走同一套门禁判定。

## 3. 验收标准

| # | 场景 | 预期 |
|---|---|---|
| 1 | 仓库有历史规格，但本任务未产出规格，直接改业务源码 | 🚫 拦截 |
| 2 | 本任务已产出规格（未提交），再改业务源码 | ✅ 放行 |
| 3 | 仓库有历史证据，本任务未产出证据，直接写端到端测试 | 🚫 拦截 |
| 4 | 本任务已产出新鲜证据，再写端到端测试 | ✅ 放行 |
| 5 | 改动集合含界面源码但无端到端测试，执行提交/推送/建 PR | 🚫 拦截 |
| 6 | 改动集合含界面源码且含端到端测试 | ✅ 放行 |
| 7 | 改动集合不含界面源码（纯服务端/脚本） | ✅ 放行 |
| 8 | 通过 bash 重定向绕过改写业务源码且本任务无规格 | 🚫 拦截 |
| 9 | 写规格文档本身、改脚本/文档/配置 | ✅ 放行 |

## 4. 边界

- 开发版应用的运行时验收由**人工**执行，门禁**不得**对开发版运行时验收设卡（用户明确约定）。
- 门禁只约束「规格 / 验证证据 / 端到端完整性」三项，不新增其他流程卡点。
