# 规范：X Article 长文海报默认分页模式

- Issue: [#4001](https://github.com/omnimux-ai/omnimux-dsh/issues/4001)
- 影响插件：`plugins/omnimux-browser`（扩展 content script / compose hand-off）
- 风险：R2（单插件常规变更）

## 1. 问题与目标

现有点赞海报（#3460）只为单条短推文设计：正文 40px、行高 68px、固定宽 1280，高度上限 4000px；超出时 `fitPosterLines()` 直接截断并补省略号。2026-11-08 线上实测 X Article `https://x.com/lifesinger/status/2118936739654046143`（95 段 / 9,469 字）：生成 1280×3974 PNG，只显示约 1,113 字（11.8%），第一章末尾即出现「…」，后续全部丢失。

用户已确认产品行为：**超过单张海报容量后，默认就只能是分页模式**。

目标：同一篇长文生成多张可读的 3:4 海报页，发帖页自动附加全部页面并继续预填观点；短推文仍保持原单张海报；任何情况下都不自动发布。

## 2. 用户流程

1. 用户在 X 时间线/详情页（含 X Article 详情页）点击海报入口。
2. 模态照旧选择白底/黑底。
3. 确认后：
   - 内容仍在单张容量内 → 生成一张宽 1280、高度随行数变化的 PNG（最高 3974），行为与现状一致。
   - 内容超出单张容量 → 自动分页生成多张 1920×2560（3:4）PNG，最多 4 张；无截断省略号。
4. 生成完成后跳转 `https://x.com/compose/post`，一次性把所有页面作为图片附件加入发帖框，并预填个人观点。
5. 用户自行确认后发布；任何路径都不点击发布按钮。

## 3. 分页规则

### 3.1 单张判定

使用现有单张布局的换行结果：正文 40px、行高 68px、内容宽 1080、最多 `maxPosterBodyLines()`（53）行。未超过时走原 `renderPoster()`，不改变短推文输出尺寸。

超过旧单张容量、但长文页布局能在 3:4 页内完整装下时，仍使用长文页布局（可能只有 1 页），不回到旧单张尺寸。

### 3.2 长文页布局

- 页面尺寸：`1920×2560`（3:4，X 单图完整展示区间内）。
- 页面内边距：120px；作者头部高 200px；水印区高 120px。
- 正文：24px 字体、40px 行高、段间距 12px，按自然段边界分页；页内 `2,120px` 可用正文高度。
- 字体自适应：依次尝试 24 / 22 / 20 / 18px 字号（行高、段间距按比例缩放），取第一个不超过 4 页的布局。
- 最多 4 页（X 单帖最多 4 张图）。18px 仍超过 4 页时抛出明确错误，不生成残缺图。
- 每页绘制：作者头像/名称/认证标识（沿用现有绘制函数）、分隔线、正文、右下角 OmniMux 水印、左下角 `页码 / 总页数`。
- 分页只拆分自然段；单段超长时按行拆分，不改变文字内容；不补省略号。

### 3.3 文字读取

- 使用现有 `extractTweetCapture()` 读取作者、地址与元数据；海报文本改从 `readTweetBody(article, undefined, Number.MAX_SAFE_INTEGER)` 读取完整标题+正文，不受模型 prompt 的 8,000 字预算影响。
- `readArticleText()` / `readTweetBody()` / `readCardText()` 新增可选 `maxChars` 参数，默认仍为 `ARTICLE_TEXT_MAX_CHARS=8000`；所有 copilot / 采集调用保持默认值，只有海报视觉导出传 `Infinity`。
- 这样同一篇 9,469 字文章在 4 页内完整显示，不会因 prompt 预算在进画布前掉 1,469 字。

## 4. 数据契约

`PendingPosterPayload` 扩展为有序页面数组，同时兼容旧单页载荷：

```ts
interface PendingPosterPayload {
  dataUrls: string[]   // 至少 1 张，按页序
  dataUrl?: string     // 旧版单页字段；读取时兼容，多页写入不再重复保存首张
  text: string
  sourceUrl: string
  theme: PosterTheme
  createdAt: number
}
```

- 存储键保持 `omnimux_x_poster_pending`；TTL 10 分钟。
- 载荷总大小沿用 `POSTER_PENDING_MAX_BYTES` 保护（8MB）；超限视为「海报过大」，中止跳转。
- `parsePendingPoster` 接受 `dataUrls` 或旧 `dataUrl`，过滤非法 PNG data URL；空数组/非法返回 `null`。
- 发帖页一次 `DataTransfer` 加入所有 `File`（`omnimux-poster-1.png` …），派发一次 `change`。

## 5. 失败与降级

| 场景 | 行为 |
| --- | --- |
| 分页后超过 4 页（18px 仍放不下） | 模态显示「内容过长，单帖最多 4 页」，不跳转、不生成残缺图 |
| 载荷总大小超过 8MB | 显示「海报过大，请重试」，不跳转 |
| 模型离线/超时 | 仍附加全部海报并跳转，观点为空，Toast 提示手动补充 |
| 发帖页未出现 composer | 保留载荷 10 分钟并提示登录 |
| 发帖页只有部分图片附加成功 | 按实际附加数量提示；不覆盖已有正文 |

## 6. 非目标

- 不做摘要封面卡、不做文章内图片/视频拼接、不做模板编辑器。
- 不自动发布、不自动创建多帖 thread。
- 不新增 manifest 主机权限；不加 `unlimitedStorage`。
- 不改短推文单张海报的视觉与尺寸。

## 7. 验收

1. **长文完整**：9,469 字 X Article 生成 4 页，每页 1920×2560；四页文字拼接后与输入 `source.text`（完整标题+正文）一致（无省略号、无丢段）。
2. **短推文不回归**：普通短推文仍为单张 1280×3974，尺寸与主题 token 不变。
3. **上限行为**：构造超过 4 页 18px 容量的文本 → 报错，不产出残缺海报。
4. **载荷兼容**：旧 `{dataUrl}` 载荷仍能读取并附加；新 `{dataUrls}` 多页载荷往返存储正确；总大小超限拒绝。
5. **发帖页**：一次 `change` 事件中 file input 收到 4 个 `File`，名称按页序。
6. **真机**：隔离 worktree 中用 `scripts/lib/extension-e2e.mjs` 启动受控 Chrome 加载扩展，在 X Article 结构 fixture 执行完整流程，保存 4 张附件 PNG 与结构化报告。

## 8. 新用户基线

不依赖开发机状态：海报渲染纯本地 canvas；头像通过现有 background 图片通道获取（失败时首字母占位）；观点依赖本机 OmniMux Host（失败时为空并提示）；不新增权限、不访问第三方服务、不在扩展外保存海报数据。

## 9. 文档影响

新增本任务规格；`specs/browser-x-poster.spec.md` 的 §5 高度上限规则由本规格补充为「单张上限；超出自动分页」，其余 v1 规则不变。本变更不涉及产品 `docs/` 外部契约。

## 假设

- X 单帖最多允许 4 张图片；3:4 页面处于 X 单图完整展示区间，适合作为分页画布。
- 1920×2560、24px/40px 的页面在 4 页内可容纳约 9,500 字的 X Article 正文（实测 9,469 字为 4 页）；超过时降字号到 18px 仍不可行则明确报错是可接受的边界。
- 扩展 content script 在发帖页仍能读取 `chrome.storage.local` 中的多页 data URL，`chrome.storage.local` 的可用配额足以容纳 4 张 1920×2560 PNG。

## 证伪方式

- 用本规格的 9,469 字文章实测：若页面数超过 4、正文出现省略号、末页缺少最后一段，或发帖页 file input 的 `files.length < 4`，则分页实现无效。
- 用短推文重跑原有海报流程：若输出不再是 1280×3974 单张，或原有 29 个海报单测出现回归，则说明分页判定误伤短内容。
- 构造 18px 仍超过 4 页的文本：若仍生成残缺图而不是明确报错，则上限降级无效。
- 用旧 `{dataUrl}` 载荷跑发帖页：若无法附加，则兼容性断言失败。
