# 规格说明：两道门禁方向冲突的收敛（规格门禁按目标仓库判定 + 物化洁净门禁区分草稿）

**文件：** `specs/gate-conflict-convergence.spec.md` ｜ **优先级：** P0

## 1. 问题：两道门禁方向相反

多 Agent 实测暴露出一组互相打架的规则：

| 门禁 | 实现 | 要求 | 副作用 |
| --- | --- | --- | --- |
| 规格门禁 | `scripts/guard-quality-loop.mjs` | 本任务规格必须出现在**判定所用仓库**的未提交改动里 | 判定用的仓库取的是「会话工作目录」而非「被改文件所在仓库」，导致在工作树里干活时判定落在主检出上 → 迫使 Agent 把规格草稿镜像进主检出 |
| 物化洁净门禁 | `scripts/sync-main.sh` | 主检出**一个未提交文件都不能有**（含未跟踪） | 主检出一旦有草稿（规格/调查/记录）就拒绝物化 |

后果：一道推着把草稿放进主检出，另一道因为主检出有草稿就罢工；而「主检出有没有草稿」与「要物化的东西是否干净」本无因果关系。

## 2. 实测取证（变更前）

- 探针一：会话工作目录＝主检出，编辑**工作树内**业务源码 → `allow`。
  说明规格门禁在工作树场景下**失效**：被改文件相对主检出落在 `.worktrees/**`，不匹配业务源码判定，直接放行。
- 探针二：会话工作目录＝工作树，编辑工作树业务源码 → `allow`（工作树内已有其它未提交规格）。
- `scripts/sync-main.sh:22-29` 用 `status --porcelain --untracked-files=all`，任何未跟踪草稿都触发 `❌ sync: 工作区有未提交改动，拒绝物化。`

## 3. 收敛设计

### 3.1 规格门禁：按「被改文件所在仓库」判定（治本）
- `edit` / `write`：任务仓库取**目标文件所在仓库根**（`findRepoRoot(dirname(target))`），业务源码判定与规格判定都在该仓库内进行。
- `bash`：优先取命令里显式声明的 `-C <path>` 目标仓库；无 `-C` 时回落到会话工作目录。
- 效果：在工作树里干活就查工作树的规格，**不再需要把草稿镜像进主检出**；主检出恢复真正只读。

### 3.2 物化洁净门禁：区分「草稿」与「会影响产物的改动」
- **已跟踪文件的任何改动** → 仍然拒绝物化（跟踪文件必然属于源码）。
- **未跟踪文件** → 仅当位于**会进入产物的路径**时才拒绝；位于草稿白名单（`specs/`、`docs/`、`tmp/`、`.workbuddy/`、`.agent-backups/`、`.worktrees/`）时放行。
- 效果：规格/调查/记录类草稿不再误伤安装；真正可能污染产物的未跟踪文件依旧拦住。

## 4. 验收标准

| # | 场景 | 预期 |
| --- | --- | --- |
| 1 | 会话在主检出，编辑工作树业务源码且工作树**无**本任务规格 | 🚫 拒绝（规格门禁在工作树内真正生效） |
| 2 | 会话在主检出，编辑工作树业务源码且工作树**有**本任务规格 | ✅ 放行 |
| 3 | 编辑主检出业务源码且主检出无本任务规格 | 🚫 拒绝（既有行为不变） |
| 4 | 主检出仅有 `specs/` 未跟踪草稿 | ✅ 允许物化 |
| 5 | 主检出存在已跟踪文件改动 | 🚫 拒绝物化 |
| 6 | 主检出存在 `plugins/` 下未跟踪文件 | 🚫 拒绝物化 |
| 7 | 工作树内正常开发（规格 + 代码） | ✅ 全程无需触碰主检出 |
