# 合并后自动物化的刷新一致性规格（Issue #1981）

## 问题与目标

`worktree.sh ship/remove` 在自动物化成功后只调用 `reload-dev-app.mjs`，而该脚本仅通过 CDP 向渲染端发送 `Page.reload`。
Client 产物由 Web 服务按请求从磁盘读取，刷新页面即取得新版本；宿主 Node 进程内的插件模块在启动时一次性载入，**不会**随磁盘文件更新。
因此服务端插件变更（新增/修改宿主 HTTP 路由、清单、构建期入口）会留下「新前端 + 旧后端」的混装状态：新 UI 调用了宿主还不存在的路由。

目标：物化收尾的刷新动作与变更面匹配——需要宿主重新加载时执行**受控重启**，纯 Client 变更仍沿用页面刷新。

## 验收标准

- **AC-1** 变更路径全部落在 `plugins/<plugin>/src/client/` 之下时，只执行页面刷新，不触发重启。
- **AC-2** 变更路径中存在 `plugins/` 下任何**非** `src/client/` 的文件时，执行受控重启分支。
- **AC-3** 变更中不含 `plugins/` 文件时，沿用现有行为：不物化、不刷新、不重启。
- **AC-4** 重启分支在目标 Dev 实例未运行时不得启动任何进程，输出跳过说明，整体退出码为 0（不阻断 ship）。
- **AC-5** 目标身份双重核实：命令行必须包含开发版包内部的 `/Contents/` 路径片段，且不含正式版包路径；仅在命令行里提到该路径的其它进程（例如某条 shell）不计入。
- **AC-6** 退出必须走优雅路径。等待退出超时（存在未保存工作、活跃生成或并发占用）时放弃本次重启、**不得**补发任何强杀信号，如实报告为「需人工协调」，退出码为 0。
- **AC-7** 重新拉起后必须等到 CDP 调试端口重新应答并出现页面目标才报告成功；超时未就绪必须报告失败，不得声明重启成功。
- **AC-8** 目标必须同时是「已核实的开发版主进程」与「CDP 端口上的监听进程」；端口上没有已核实实例时（未就绪、被其他程序占用）不做任何动作。
- **AC-9** 存在第二个开发版**实例**（例如其他任务或人工并用同一 App 二进制）时放弃重启并报告冲突，不触碰其中任何一个进程。
- **AC-10** 手动入口 `node scripts/omnimux.mjs restart dev|prod` 的既有行为与 Agent 会话拦截保持不变。

## 非目标

- 不引入宿主侧插件热重载或 HMR。
- 不改动 Prod（`~/.omnimux`）的重启授权边界。
- 不改变 `sync-to-app.sh` 的物化事务与构建顺序。

## 验证方式

- `node --test scripts/worktree-delivery.test.mjs`：fixture 仓库断言 AC-1/AC-2 的分支选择与 AC-3 的跳过路径。
- `node --test scripts/worktree-delivery.test.mjs`：以注入的进程探针断言 AC-4/AC-5/AC-6/AC-7/AC-8/AC-9 的决策与「不发送强杀信号」约束；同一文件内的 ship fixture 用例断言 AC-1/AC-2 的分支选择。
- 真实 Dev 实例一次人工触发：确认优雅退出、重新拉起、CDP 就绪判定与就绪前的宿主路由可用性。
