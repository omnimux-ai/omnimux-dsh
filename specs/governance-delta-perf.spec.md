# 静默兜底增量扫描性能修复（#3510）

## 背景与问题

PR #3492 的交付门禁对每个改动文件各起一次 `git show` 取基线，实测：10 文件 613ms、40 文件 1209ms、200 文件 1767ms。交付钩子预算 8s、`MAX_FILES = 300`，大 PR 逼近超时，且每次 commit 都有可感知卡顿。

## 假设

延迟来自「一次比较一个 git 进程」，而不是扫描逻辑本身：`scanContent()` 是纯字符串处理，单文件微秒级。因此只要把基线读取从 N 次进程降为 1 次批量读取，并在读基线前用当前内容做廉价预筛（不含 `catch` 的文件不可能新增 SC1/SC2），就能把耗时压到与文件数弱相关。

## 证伪方式

若假设成立，同一改动集下耗时应从「线性于文件数」变为「基本恒定」：10 与 200 文件的耗时差应远小于原来的 3 倍以上差距。具体观测：修复前 10 文件 613ms / 200 文件 1767ms；修复后若 200 文件仍 >300ms，或耗时仍随文件数线性增长，则假设被证伪，应改为异步/缓存方案。

## 可测验收标准

- A1 `readBlobsAtRef()` 一次 `git cat-file --batch` 读取多个基线 blob；缺失路径映射为 null。
- A2 预筛：当前内容不含 `catch` 时跳过基线读取。
- A3 已跟踪文件新增空 catch 被检出；只做无关改动不误报；删除 catch 体内日志（SC3→SC1）被检出。
- A4 200 业务文件实测 <300ms。
- A5 判定口径不变：键仍为 `path|rule|bodyKey`，按次数做差集。
- A6 `node --test scripts/lib/silent-catch-delta.test.mjs scripts/guard-quality-loop.test.mjs` 中新增用例全绿。

## 非目标

- 不改 SC1/SC2/SC3 规则与阈值。
- 不改 allowlist 结构。
- 不引入新依赖。
- 不做跨进程缓存（当前一次批量读取已足够）。

## 新用户基线

只影响仓库开发门禁，不进入产品运行时；无新增依赖。
