# 深度视频运行态自愈（Issue #3586）

## 背景

深度转换是一次同步请求：实测用户素材（8.75s / 576×1024 / 24fps）在 CPU 上耗时 **56.6 秒**。请求在 Dev 宿主重启（部署自动 Host Reload）或页面刷新（Cmd+R）时被中断，但画布持久化节点仍是 `executionStatus: 'running'`。

画布加载后无人收敛该状态，且 `planVideoDepthProvisioning` 对 running 下游节点返回 `noop`，用户再点源视频胶囊也不会重跑——表现为「生成中…」永久卡住、无法恢复。

## 修复范围

- 模块级活跃集合（`activeDepthTargets: Set<nodeId>`）：深度请求开始时登记，`finally` 移除。
- `planVideoDepthProvisioning` 新增活跃判定参数：`running` 且活跃 → `noop`（防抖，保持现有行为）；`running` 但非活跃 → `update`（清旧媒体、重新 running、真正重跑）。
- 派生节点自愈：节点 `origin === 'video_depth'` 且 `executionStatus === 'running'`，但不在活跃集合时，收敛为 error（`depthVideo.toast.interrupted`：上次深度视频转换被中断，请重试），露出「重新生成」；源视频节点不动。
- 不改请求方式、转换耗时与推理参数。

## 用户旅程

1. 转换被打断后重新打开画布：派生节点显示「上次深度视频转换被中断，请重试」，可点「重新生成」或重新点源视频「深度视频」。
2. 转换真正进行中时刷新/重载：新渲染器活跃集合为空，节点收敛为中断错误（不会无限等待），用户可安全重试。
3. 正常进行中再次点击源视频胶囊：仍在活跃集合 → noop，不重复提交。

## 验收

- [ ] 单测：planner `running + active` → noop；`running + inactive` → update 且清媒体；自愈仅命中 `origin==='video_depth'` 的 running 节点。
- [ ] 浏览器：构造 running 深度节点（无活跃请求）→ 自动显示中断错误 + 重新生成；点源胶囊 → 第二次 `POST /video-depth` 成功收敛；截图 + JSON 证据。
- [ ] 非目标：不改转换耗时/参数、不做进度百分比、不改后台任务化、不动音频提取同类历史问题。

## 新用户基线

纯客户端状态自愈，不引入本机状态、凭据或新服务依赖；对全新安装环境行为一致。

## 假设

- 页面加载后不存在「由其它渲染器/窗口继续执行的深度请求」：深度转换没有服务端任务台账，只有发起它的那个渲染器可能拿到结果，因此重载后任何 running 深度节点都应视为已中断且可重试。
- 活跃集合只覆盖本渲染器内的请求；同一画布多窗口并发转换不是现有产品形态。

## 证伪方式

- 若浏览器中构造的 running 深度节点加载后仍显示「生成中…」且没有重试入口，说明自愈未生效或作用域不对，用截图与节点 state 复核并修正。
- 若正常进行中的转换被误判为中断（节点在请求未结束时就变 error），说明活跃集合登记/清理顺序有误，应以「请求开始即登记、finally 清理」复核。
- 若再次点击源胶囊仍 noop，说明 planning 没拿到活跃判定，需检查调用参数。

## 非目标

- 把深度转换改成服务端任务队列或断点续跑。
- 进度百分比/流式事件。
- 修改推理参数与耗时（另开性能任务）。
