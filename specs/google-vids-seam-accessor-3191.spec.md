# Google Vids 取中枢生成缝的真机可用性修复规格

- **Issue**: #3191
- **关联**: #3186（四模式接入中枢本机视频通道，PR #3187 已合入）
- **状态**: 真机复检发现阻断性缺陷，本规格为修复前置

## 1. 问题与用户旅程
面板「创建/添加动画/修改/延续」四种用法都要经插件 HTTP → 中枢生成缝 → 本机视频通道产出成片。真机复检发现：在运行中的应用内请求插件自身接口，健康检查直接 500，报错为「未声明服务属性不可读取」。

用户旅程：打开 Google Vids → 填描述 → 点生成 → 应得到任务编号并轮询到成片。当前在第 3 步即失败，且失败原因与用户输入无关。

## 2. 根因
宿主对**未在本插件 `inject` 中声明的服务属性**执行读取时抛错，而不是返回 `undefined`。因此 `ctx.<缝名> ?? ctx.get?.(<缝名>)` 这种写法里，`??` 右侧的兜底永远不会执行；缝取不到 → 依赖该缝的所有路由直接失败，连「回退到插件自带驱动」的分支也走不到。

## 3. 行为契约
1. 缝的解析只经安全取值通道；宿主未提供、取值抛错、访问器缺失，三种情况一律按「未提供」处理并回退插件自带驱动。
2. 宿主提供该缝且形如 `{ execute }` 时，选中中枢通道；四种用法的上游操作映射保持不变。
3. 不因该缝而改变插件的装载条件：中枢缺席时插件照常装载，自带驱动可用。
4. 不新增宿主槽位、不改动对外 HTTP 契约与轮询语义。

## 4. 验收用例
- 回归：用「未声明属性读取即抛错」的上下文替身驱动解析，必须不抛错且判定为「未提供」；修前该用例必须失败。
- 正例：替身提供形如 `{ execute }` 的缝时被选中。
- 反例：访问器缺失、访问器自身抛错时均按「未提供」处理。
- 现有回归：`pnpm --filter omnimux-video test`、`tests/e2e/google-vids-hub-wiring.e2e.test.mjs`、`pnpm verify:plugin-load`、`pnpm test:plugin-load`、`pnpm verify:stages`、`pnpm check:boundaries`、`pnpm verify:product-baseline` 全绿。
- 真机：修复物化后，同一接口请求不再返回该错误；四模式之一能拿到任务编号。

## 5. 边界
仅修取缝方式与该类回归测试；不重构路由、不改模式映射、不触碰前端。
