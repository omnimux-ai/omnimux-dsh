# worktree.sh ship 收尾横幅按真实物化状态描述（#3700）

- Issue: #3700
- 日期: 2026-10-24
- 基线: 分叉点 `45b21bc5a`（合入前对齐 `origin/main`）
- 触发事实: PR #3694 的 `ship` 输出中，「⚠️ 自动物化未成功」与下一行「✅ …开发版已物化」直接矛盾；核对 `~/.omnimux-dev` 后确认新文件不在 Dev。

## 1. 现状

`auto_materialize_and_reload()` 有 6 条返回路径，其中 3 条属于「开发版未更新」：

| 行 | 情形 | 现状 |
| --- | --- | --- |
| 397 | 缺少 `scripts/sync-to-app.sh` | 只打警告，返回 0 |
| 411 / 420 | 只改文档/测试，或没有插件源码 | 无需物化，返回 0 |
| 434 | Dev 已包含该范围 | 跳过重复安装，返回 0 |
| 448 | `sync-to-app.sh` 成功 | 打「✅ 增量物化成功」 |
| 466 | `sync-to-app.sh` 失败 | 只打警告，返回 0 |
| 631 | 无法确定合并起点 | 只打警告 |

`cmd_ship` 的两处收尾横幅（527 行的英文行与 536 行的中文行）是硬编码文案，不读上述结果，因此在失败路径也会宣称「开发版已物化」。

## 2. 方案

1. 新增脚本级变量 `MATERIALIZE_STATUS`，在上述每条路径显式赋值：`ok` / `already-current` / `not-needed` / `failed` / `unknown`。
2. 新增 `materialize_dev_state()` 把状态翻译成中文分句；收尾横幅改为拼接该分句。
3. 失败路径在横幅之外**额外**输出一行可执行补救命令（`./scripts/sync-to-app.sh`），并明确「PR 已合入、主干已同步、开发版未更新」三段事实。
4. 保留「交付全链路闭环完成」作为收尾框架句：既有用例断言该短语（`scripts/worktree-delivery.test.mjs:52`），保留它同时把开发版分句改成真话。
5. **不改退出码语义**：合并已确认时 `ship` 仍返回 0（物化失败不是合并失败），与 `plugin-git-pr` 的「物化失败留下明确提示并继续可行修复」一致。

## 3. 验收

- `node --test scripts/worktree-delivery.test.mjs`：既有断言不削弱；新增用例覆盖
  「物化失败 → 输出含『开发版未更新』且不含『开发版已物化』」与「物化成功 → 输出含『开发版已物化』」。
- `pnpm test:gates` 通过。
- 手工复核：`MATERIALIZE_STATUS` 的每个取值都有对应的横幅文案，无 `unknown` 落到「已物化」。

## 假设

- `sync-to-app.sh` 的退出码就是物化成败的判据：成功即 Dev 已装入本次插件改动，失败即未装入；脚本内部若部分写入，本改动不做二次校验（现有 `dev-smoke.mjs` 仍是唯一运行期冒烟）。
- 「开发版已包含本次合入」与「无需物化」在用户视角都不是失败，因此横幅应分别说明，而不是统一写成「已物化」。
- 既有用例断言的是「交付全链路闭环完成」这一收尾框架句，而不是「开发版已物化」，因此修正分句不构成削弱既有标准。

## 证伪方式

- 造一个 `sync-to-app.sh` 返回非 0 的 fixture 跑 `ship`：若 stdout 仍出现「开发版已物化」，则修复无效。
- 造一个 `sync-to-app.sh` 返回 0 的 fixture 跑 `ship`：若 stdout 不出现「开发版已物化」，则文案映射写反。
- 只改文档的 fixture（既有用例 669/694/745 行）：若横幅不再含「无需物化」，则状态映射与既有语义冲突。
