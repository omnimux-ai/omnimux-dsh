## 2. Python 缺失：恢复兼容要求，不追认全库停用

### 2.1 产品裁定

1. **不允许按现授权交付“同一原已支持 macOS 环境，仅因没有 Python，全部旧资产库 API/UI/工具不可用”。** C:120 的选项①不是已获准的默认值；“支持平台”文案不能把新依赖导致的回归包装为用户同意。
2. **既有兼容仍是要求，不是待用户选择的新增需求。** 在健康旧库、未启动新根迁移且原环境可用的前提下，应保留既有资产查询、详情/预览、普通导入及相关写操作、legacy 兼容和既有 HTTP/工具消费语义；不允许只留下空列表或只读页便称完全兼容。普通导入仍 copy，项目 instantiate/promote/快照规则不变（P:62、72、85、308；A:30–31、332–340、576）。不新增原来不存在的功能。
3. **不能为恢复兼容绕过安全要求。** 当前架构中的安全 FD/no-follow、身份校验、锁和恢复屏障继续有效；不批准不安全 JS fallback、捕获缺助手错误后开无保护 store、按绝对路径重开预览流，或把测试替身带入生产（A:44–46、338、343；R:21）。
4. 当前实现如果暂时只能 fail-closed，应保留安全失败并明确报告“兼容未完成”，不能为了验收绿灯开放不安全 I/O。**安全拒绝是开发中的保护状态，不是完成旧库兼容，更不是批准上线该退化。** 技术上不能同时满足时，暂停对应交付结论，继续其他已授权开发。
5. 坏账本、掉盘、根身份变化、进行中事务或已切换自定义根的安全能力丢失，仍按既有恢复/离线规则处理。不得以本次“旧库兼容”裁定直接切回旧根写入、绕恢复屏障或创建默认空库（P:175–185、246；A:120、411–422）。健康旧库兼容与故障恢复是不同场景。

### 2.2 新迁移、安装与发布边界

- 无 Python/必需安全能力时，新迁移明确 `storage-platform-unsupported`，无媒体变更；能力及原因可见，不假成功（A:46；C:119–121）。不得自动安装 Python 或修改系统环境来消除提示。
- 原架构允许使用已可调用的窄 Python 标准库助手，并要求验证 L2/包中的实际可用性；本机探测不证明客户或打包环境具备能力（A:36–46、529）。沿用当前助手开发不是获准供应新的系统依赖。
- 本裁定不指定新的实现方案，也不自主批准原生 helper、捆绑解释器、安装器、签名/分发调整或桌面/官方仓修改。A:513 的“另行批准”仍是条件，不能用产品角色或主理人的内部派工代替所需用户授权。
- 在现有授权和本仓边界内评估、修复安全兼容路径可以继续；可行性须由工程/架构给证据。不能事先宣称某个无依赖兼容方案必然可行。

### 2.3 必需验收证据（非已通过）

在隔离样本分别验证：有助手的既有/新迁移链路；同一已支持 macOS 无助手的健康旧库兼容；新迁移的明确能力阻断且零媒体变更；事务中/切根后丢失能力的安全拒绝与恢复。覆盖实际 HTTP、工具与 UI 消费，不以路径解析通过或“501 正确”代替旧功能兼容。原 A01–A17 不缩减，也不扩为全平台运行保证。

## 3. 关键元数据：按有限支持条款保守阻断可以闭合

### 3.1 必须区分两类元数据

- **业务元数据和已知合法引用是保留义务，不是“尽力”。** 名称、分类、描述、标签、封面、来源、时间字段及 file/asset/artifact/mapping 关系按已知 schema 保留和映射（P:96、195–196、300；A:125–129、297）。不能借文件系统属性例外丢业务字段。
- **文件系统属性采用本次支持平台的必要语义。** 普通 POSIX mode/mtime 按 A:489 保留与复核，不设 setuid/setgid，不递归 chmod 用户树。ACL、xattr/resource fork 及其他无法证明可保留的重要语义，在预检告知、阻断相应变更并留原处。P:238 没有承诺所有 OS 的所有元数据自动复制。

### 3.2 本次可执行的保守判据

1. 无已确认可忽略规则时，将检测到的 ACL、xattr/resource fork 视为潜在关键属性；不得自行把 quarantine 或未知属性白名单化。无法读取、无法判断是否存在或无法验证目标能力，不等于“没有属性”。该判据是保守保护方式，不宣布每种属性都必须提供自动复制器。
2. 检查必须覆盖来源复制、目标被覆盖旧版本/补偿、目录自身属性及 reuse 兼容性。不能只查来源 xattr，就允许覆盖带 ACL/xattr 的目标；也不能只证明文件字节 hash 相等，就认定权限/时间等语义等价（C:95–102）。
3. 无法证明保留时，**阻断该复制/覆盖/整理/reuse**；原来源与旧目标内容及属性不变。可证明不改属性且可安全纳管的目标原位项仍可原位使用，不为保护而复制整树。不能确定影响边界时扩大到必要的相关记录/操作阻断，不继续破坏性步骤。
4. 预检、计划、结果均明确条目、原因、影响引用及保留/恢复位置。来源因此未迁入的项纳入实际完整 partial 集合；经用户对该集合确认后，才可完成有跳过项的切换。不能静默消失、错误指向异内容目标或标记全部成功（P:154、184–186、227、251；C:71–79）。
5. 跳过项、唯一副本及其恢复信息不清理；被记录继续引用的旧版本不是可按天清理的备份（P:264–267；A:301–303、322）。如果元数据不足以保证恢复，就不能先覆盖后再报告。

**闭合条件：**上述检测、拒绝、用户可见报告、完整 partial 确认、原件/目标不变和恢复/清理保护均有实际测试证据，即可满足这一有限条款；不需要等待全平台属性复制器。只有把条目标成 `unmigrated` 或保留英文 reason，不算闭合。该结论只关闭元数据支持范围歧义，不关闭 #766 其他 P0。

无需向用户逐种询问属性是否关键才能继续保守保护。若后来明确要求“这些当前不支持的属性也必须自动搬迁”或“允许丢弃某种属性”，才是额外能力/数据语义变更，须具体披露后另行确认；当前不作这种推定。
