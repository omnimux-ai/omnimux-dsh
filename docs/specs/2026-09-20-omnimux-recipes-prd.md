## 一、战略背景与定位

### 1.1 业务定位

在原有「爆款视频复刻」能力之上，向**上游业务场景**延伸：帮商家做**电商视频的批量生产**。

第一阶段的产品定义非常克制：**商家给一个商品，我们批量出素材，他拿去测试。** 判定标准不是"视频做得多精美"，而是**商家用最低成本、最快速度测出「哪种表达方式对这个商品有效」**。

### 1.2 核心痛点与解决思路

| 商家真实困境 | 传统做法的问题 | 本产品的解题方式 |
| :--- | :--- | :--- |
| 不懂怎么做视频，不知道该怎么表达商品 | 找代运营/MCN，一条几百块，周期以周计 | 商品链接进来直接出成片，按条计价、分钟级 |
| 复刻别人的爆款容易被平台判定重复 | 逐条复刻，批量多了必被剥离 | **迁移节奏骨架，不搬运素材**（`take/adapt/ignore` 决策矩阵） |
| 让 AI 自由发挥，结果不靠谱、跑偏 | 提示词越写越长，产出仍然同质化 | **受控组合**：产出量来自枚举池的组合，不来自模型想象力 |
| 出了一堆素材，但不知道哪条为什么好 | 数据回来只看整体表现，无法归因 | **配方指纹**：每条素材可追溯到具体变量组合 |

### 1.3 关键业务认知（本方案的两个基石）

**认知一：把"创意"从模型能力问题，重构成"枚举组合"问题。**

商家说"我不知道该怎么表达这个产品"，本质是**变量维度太多、组合空间太大**，不是 AI 不够聪明。解法是把创意拆成四层正交变量（人设 / 结构 / 画面 / 平台），每层挂一个**已验证手法**的枚举池，用受控组合代替自由创作。产出量 = 池子的笛卡尔积，可追溯、可复现、可去重。

**认知二：要"基于数据固化模板"，就必须用正交实验设计（DOE），不能用随机数。**

这是本产品最关键的工程决策。

假设人设层 8 个水平、Hook 层 15 个水平，出 12 条**随机**组合，实际分布往往是这样：

```
人设分布：  宝妈 ×5，测评博主 ×4，健身教练 ×3，其余 5 个水平 ×0
Hook 分布： 痛点直击 ×4，悬念提问 ×3，其余 13 个水平分布稀疏
```

数据回来只能看到"这批整体完播 25%"。**无法回答是 Hook 起作用、人设起作用，还是二者交互**——因为某些水平根本没样本。那"固化模板"就只能靠感觉。

正交表保证：同样 12 条素材，每个变量的每个水平出现次数相等、两两组合均匀覆盖。**12 条 = 12 个可归因的观测**，而不是 12 个孤立样本。

### 1.4 两阶段闭环（产品主线）

```
探索期（测模板）          收敛期（固化）            复用期
多样性最大化      →      可归因后冻结      →      新商品套模板跑量
变量矩阵展开 N 条         胜出组合析出为模板        成本最低
每条带唯一配方指纹        落工作流模板库            模板衰减则回流探索
```

> 本版 PRD **只交付探索期**（S1～S4）。收敛期（S5）依赖数据回流，见 §十 风险与依赖。
>
> **配套的验收主线见 §八 递进式验收**：探索期内部再按「分镜脚本 → 角色分镜图 → 成片」三关递进，不追求一步到位。

#### 资产 B：灵感库解构能力（schema 完整，但数据近乎为空）

**数据结构**（`~/.dsh/omnimux/inspirations/library.json`，每条 item 含）：

| 字段 | 内容 | 对本产品的价值 |
| :--- | :--- | :--- |
| `hook_highlight` | 黄金前 3 秒钩子（视觉反差 / 痛点唤醒 / 情绪基调） | **Hook 变量池的实例来源** |
| `target_goal` | 转化目标 / 情绪基调 / 爆款基因 | 目标与情绪维度 |

| `visual_breakdown` | 场景设置 / 镜头语言 / 节奏特征 + 逐帧拆解表 | 画面层变量池 |
| `replication_action` | **复刻公式** + 创作建议 | ★ **直接可解析为结构枚举** |

**复刻公式的格式**（真实样例）：

```
[痛点反问/冲突开场] + [产品第一人称实测] + [视觉效果即时展示] + [引导主页 Bio 下单]
```

**这是一个天然可解析的结构模板语法**——每个 `[...]` 就是一个可枚举的槽位。用它可以直接生成"叙事结构"维度的池子。

**⚠️ 现状风险（必须处理）**：

| 问题 | 证据 | 影响 |
| :--- | :--- | :--- |
| **灵感库数据几乎为空** | 生产库 `~/.dsh/omnimux/inspirations/library.json` 仅 **1 条**；开发库 1 条测试数据 | 无种子数据，无法直接作为模板来源 |
| **降级路径会产出假解构** | `plugins/omnimux-inspiration/src/analyzer.js` 的 `generateSemanticDeconstruction()` 在无本地视频时，**返回硬编码示例文案**（美妆/护肤场景，含写死的 hook、叙事、分镜表） | 若误把降级产物当真实解构，会**污染变量池**（所有商品都变成同一个美妆模板） |

**处置要求**：灵感库数据进入变量池前，**必须**标记来源（真实解构 / 语义降级），降级产物一律不入池。种子数据采集走 S0 阶段，用 `omnimux-social-harvest`（9 平台）采集对标账号作品后走真实解构路径。

## 三、用户画像与典型业务旅程

### 3.1 用户画像

**主用户：中小电商卖家 / 跨境卖家 / 单品测款团队**

| 特征 | 说明 |
| :--- | :--- |
| 技能水平 | 会选品、会看数据，**不会做视频** |
| 核心诉求 | 手上有 5～20 个候选商品，想知道哪一个能跑出来 |
| 预算敏感 | 单条素材心理价位：个位数人民币 |
| 交付期待 | 拿到就能投，不需要自己剪 |

### 3.2 典型旅程（核心场景）

```
① 商家打开「配方库」一级页
② 输入商品链接 ── 或 ── 从产品库选一个已有商品
③ 系统解析商品 → 展示事实卡（名称/卖点/受众/价格/行业判定）→ 商家确认或修正
④ 选择人设（可多选：测评博主 / 宝妈 / 健身教练 …）
⑤ 设定生成数量（如每个角色 6 条，共 12 条）
⑥ 系统匹配候选模板 + 生成 12 组配方 → 展示配方预览表（每条是什么组合）
⑦ 商家确认 → 系统先渲 10 秒核心切片（Sample Gate）
⑧ 商家看切片定方向 → 确认放量 或 换一批配方
⑨ 批量生产 → 质检 → 成片入资产库
⑩ 商家导出/下载，拿去投放到目标平台
```

**关键体验点**：第 ⑥ 步的**配方预览**——商家在花钱之前就能看到"这 12 条分别是什么思路"，而不是等 20 分钟拿到一堆不知所谓的片子。这是本产品区别于"盲盒式 AI 生成"的核心体验。

## 四、核心机制

### 4.1 双引擎：模板适配 + 变量注入

老板明确要求"通过工作流自动化适配模板"。因此配方不是凭空生成，而是**从模板池里选 + 往模板里注**：

```
商品事实卡
   │
   ├─→ 【模板适配】从 94 个创意手法（112 个手法元数据中剔除 12 工具 + 6 占位）中，
   │      按「行业垂类 × 人设 × 平台」匹配出候选模板
   │      （如：美妆 + 测评博主 + TikTok → ugc-* 系列 8 个候选）
   │
   ├─→ 【变量注入】往模板的槽位注入具体参数
   │      人设身份 / Hook 类型 / 台词风格 / 画面形态 / 时长
   │
   └─→ 【正交分配】用正交表决定这批 N 条里
          选哪些模板、注哪些变量，保证水平均衡
```

**三者的关系**：

| 概念 | 定义 | 来源 |
| :--- | :--- | :--- |
| **模板（手法）** | 已验证的叙事结构 | 94 个创意手法（`ugc-unwrap` / `mirror-tryon-haul-beat-cut` …） |
| **变量** | 注入模板的参数槽 | 四层变量矩阵（见 §4.2） |
| **正交表** | 决定"这一批怎么配"的分配算法 | 新建引擎 |

### 4.2 四层变量矩阵

| 层 | 变量 | 池子来源 | 本版是否开放 |
| :--- | :--- | :--- | :--- |
| **人设层** | 行业 × 身份 × 语言 × 信任来源 | 94 个创意手法 + 106 个专家 + 5 个营销人格 | ✅ **开放** |
| **结构层** | Hook × 叙事 × 时长 × CTA | 96 款广告格式 + 75 款 Hook + 灵感库复刻公式 | ✅ **仅开放 Hook** |
| **画面层** | 形态 × 景别序列 × 机位 | 22 个 operation + 机位契约 | ⏸ 本版冻结（固定为主形态） |
| **平台层** | 渠道 × 安全区 × 时长 | 平台规则卡 | ⏸ 本版冻结（单一平台） |

> **逐轮放开纪律**：本版只放开「人设 × Hook」两个维度。维度越多，正交表规模指数增长，算力扛不住，且归因能力下降。测出胜者后再放开下一层。

### 4.3 变量池初始枚举（种子数据）

**人设层**

| 变量 | 初始水平 | 建议首期 |
| :--- | :--- | :--- |
| 行业垂类 | 美妆个护 / 保健营养 / 3C 数码 / 母婴 / 家居日用 / 服饰配饰 / 食品饮料 / 教育课程 / 宠物用品 / 汽车用品 | 池子最厚的 3 个 |
| 身份 | 测评博主 / 宝妈 / 健身教练 / 学生党 / 职场人 / 行业从业者 / 素人路人 / 专业人士 | 全部 8 个 |
| 信任来源 | 亲测体验 / 专业背书 / 素人真话 / 数据对比 / 翻车避坑 | 全部 5 个 |

**结构层（本版只开 Hook）**

| Hook 类型（15 款） |
| :--- |
| 悬念提问 / 痛点直击 / 视觉反差 / 反常识 / 结果前置 / 身份共鸣 / 价格锚点 / 场景痛点 / 冲突开场 / 数据冲击 / 悬念反转 / 挑战式 / 自嘲式 / 对比式 / 倒计时式 |

> Hook 池需与 `marketing-agent` 预设声明的「75 款开场黄金 Hook」对表核实，本版先落 15 款高频项。

### 4.4 防重复三重防线

| 防线 | 作用域 | 机制 |
| :--- | :--- | :--- |
| **组合约束** | 同批次 | 同批内 Hook 不重样、人设按配额分配（正交表天然满足） |
| **语义指纹** | 跨批次 | `商品 × 人设 × Hook × 模板` 编码为确定性指纹，入历史库，命中即换。复用 LoopGuard 的 `toolName#hash` 思路 |
| **结构变异** | 单条内部 | 景别排列 / 时长配比 / 镜头数做排列组合 |

**硬约束（引擎不可逾越）**：
- 保健 / 医药 / 金融的功效表述 → `block` 拦截
- 医药类必须走 `regulated-claims` 手法，不得自由创作功效表述
- 参考素材的原片水印 / 人脸 / 人声必须 `ignore`（静默剥离，**不写负向词**）

## 六、数据模型

### 6.1 落盘结构

```
$DSH_HOME/omnimux/<plugin>/
├── variable-registry.json    # 四层变量池 + 硬约束规则
├── template-pool.json        # 从 market catalog 同步的模板索引缓存
├── recipes/

├── batches/
│   └── <batch-id>.json       # 批次（正交表定义 + 成员配方 + 状态）
└── lineage/
    └── index.json            # 配方 → 产物 → 交付 的映射
```

### 6.2 配方（Recipe）核心字段

| 字段 | 说明 |
| :--- | :--- |
| `recipe_id` | 唯一 ID |
| `fingerprint` | `商品 × 人设 × Hook × 模板` 的确定性哈希 |
| `template_ref` | 引用的手法模板（skill slug） |
| `persona` | 人设变量值 |
| `hook_type` | Hook 变量值 |
| `seed` | 可复现随机源 |
| `batch_id` | 所属批次 |
| `artifacts[]` | 产物引用（含降级标注） |

### 6.3 血缘（Lineage）

```
recipe_id → artifact_id(s) → 交付记录
```

**这是 S5 归因的唯一依据**。本版虽不做归因，但**血缘字段必须从 S1 就完整落盘**，否则 S5 无从追溯。

**递进验收下血缘链变长**：成片 → 分镜图 → 分镜脚本 → 配方指纹。每一关新增的产物都必须挂在前一关的标识上，否则第二、三关的验收记录无法回推到配方，归因会在中途断链。

## 八、递进式验收（关键里程碑）

> ⭐ **本章是本项目的验收主线。** 核心原则：**不追求一步到位**。产出物按「分镜脚本 → 角色分镜图 → 成片」三关递进验收，**未过前关不得进入后关**。
>
> 依据：视频的最终表现是目的，但"不符合预期"这件事必须在成本最低的环节就暴露出来。一步到成片的做法，等发现问题时创意、画面、合成三层的返工成本已经叠满。

### 8.1 为什么必须递进，而不是一步到成片

| 比较项 | 第一关 分镜脚本 | 第二关 角色分镜图 | 第三关 成片 |
| :--- | :--- | :--- | :--- |
| 单条成本 | 极低（纯文本） | 中（图像生成） | 高（视频 + 配音 + 合成） |
| 产出周期 | 秒级 | 分钟级 | 分钟到小时级 |
| 能发现的问题 | 创意方向、表达准确性、手法贴合、合规 | 角色形象、商品还原、画面构图 | 动态、节奏、音画同步 |
| 发现问题后的返工面 | 只改配方或池子 | 只改画面描述 | 局部重摇，不动配方 |
| 失败信息量 | 高（知道是哪一条错） | 中 | 低（只知"不好看"，不知错在哪） |

**结论**：越早验收，单次判断成本越低、信息量越大、返工面越小。**分镜脚本是全链路投入产出比最高的一环，因此它是本项目最核心的交付物，而不是视频本身。**

### 8.2 第一关 · 分镜脚本验收（S1 主交付 · 全链路最核心）

**交付物**：指定角色与条数下的分镜脚本集，每条携带配方指纹。

**为什么这一关最重要**：脚本是创意的完整表达——脚本对不对，等于创意对不对。而脚本是纯文本，**打分成本近乎为零、迭代速度以秒计、可批量横向比对**。拿到脚本就能走评估打分，这是整个链路唯一能低成本大规模试错的位置。

**评分维度**（每项 1–5 分，人工打分）

| # | 维度 | 评什么 | 5 分 | 1 分 |
| :--- | :--- | :--- | :--- | :--- |
| G1 | Hook 强度 | 前 3 秒能否拦住划走 | 有具体冲突、悬念或数字 | 泛泛开场或直接介绍产品 |
| G2 | 卖点落地 | 卖点是否转成可感知表述 | 卖点变成场景或前后对比 | 卖点原样复述成形容词堆砌 |
| G3 | 手法贴合 | 是否真的采用了指定手法 | 结构可被识别为该手法 | 手法名只是贴了个标签 |
| G4 | 口播自然度 | 像不像真人说话 | 全口语，有停顿与语气 | 书面语，像产品说明书 |
| G5 | 画面可执行 | `visual` 能否直接喂生成模型 | 含主体、动作、景别、环境 | 抽象描述，无法生成画面 |
| G6 | 结构完整 | 时长与分镜是否在范围 | 15–45 秒、4–8 分镜、有起伏 | 超范围或缺 CTA |
| G7 | 合规 | 功效表述是否越界 | 无绝对化用语、无无据结论 | 出现疗效承诺或绝对化用语 |
| G8 | 差异化 | 同批次彼此是否明显不同 | 与同批其他条肉眼可辨 | 与同批某条几乎同构 |

**通过阈值**

| 条件 | 判定 |
| :--- | :--- |
| 8 项均分 ≥ 3.5 | 必须满足 |
| 无单项均分 ≤ 2 | 必须满足 |
| **G7 合规为否决项** | 任一条出现即该条直接不通过，不参与均分 |

**打分执行方式**

- S1 阶段以**人工打分**为准。打分人可以是商家本人或运营。
- 可先用现有营销专家子代理（`expert_ad_creative` / `conversion_copy` 人格）做**预打分**以节省人力，但**通过与否以人工判定为准**，不接受模型自评作为验收结论。
- 评分表落盘并与配方指纹绑定，形成「创意质量」的第一份数据集。

### 8.3 第二关 · 角色分镜图验收（S2 主交付）

**交付物**：每条脚本的 `shots[]` 转成关键帧图，角色形象与商品外观可视化。

**为什么要有这一关**：分镜图是**成本最低的效果预演**。一张图与一段视频回答的是同一个问题——「这条创意看起来对不对」，但成本差一个数量级。到这一关，商家第一次能"看见"视频大概长什么样。

**评分维度**（每项 1–5 分）

| # | 维度 | 评什么 |
| :--- | :--- | :--- |
| P1 | 角色一致性 | 同一角色跨分镜是否同一人（脸型、发型、服装） |
| P2 | 商品还原度 | 商品外观、颜色、包装、logo 是否与实物一致 |
| P3 | 脚本对齐度 | 每张图是否表达了对应分镜的 `visual` 描述 |
| P4 | 画面质量 | 有无畸变、肢体错误、文字乱码 |
| P5 | 合规 | 无违规宣称、无侵权形象、无平台禁用画面元素 |

**通过阈值**：P1 / P2 / P3 均分 ≥ 3.5；P4 无严重畸变；**P5 为否决项**。

> ⚠️ **本关的能力边界**：分镜图能验证构图、角色、商品呈现与画面氛围，**不能**验证动态、运镜、节奏与口播语气。因此过了这一关**不等于**成片可用，第三关不可省略。但前两关通过后第三关的失败率会大幅下降——创意与画面这两个最贵的变量已经被锁定了。

### 8.4 第三关 · 成片验收（S3）

| # | 维度 | 判定 |
| :--- | :--- | :--- |
| V1 | 可播放、可导出 | 通过 / 不通过 |
| V2 | 音画同步：口播、字幕、画面对齐 | 通过 / 不通过 |
| V3 | 节奏符合手法设定的切点节拍 | 通过 / 不通过 |
| V4 | 平台合规：无禁用语、无残留水印、主体在安全区内 | 通过 / 不通过 |
| V5 | 商家可直接投用，无需二次剪辑 | 通过 / 不通过 |

### 8.5 三关与交付阶段的映射

| 关卡 | 交付阶段 | 该阶段**只交什么** |
| :--- | :--- | :--- |
| 第一关 · 分镜脚本 | S1 | 配方 + 分镜脚本，**不出视频** |
| 第二关 · 角色分镜图 | S2 | 分镜图，**仍不出视频** |
| 第三关 · 成片 | S3 | 成片 |

**纪律**：S1 与 S2 阶段不产出视频。任何"顺手把视频也生成了"的做法都不在本版范围内——它会让验收焦点从"创意对不对"滑向"视频好不好看"，而后者是更贵、更晚、更难归因的判断。

### 8.6 功能验收明细（按关卡归属）

| # | 验收项 | 关卡 | 判定 |
| :--- | :--- | :--- | :--- |

### 8.7 性能与经济性（需实测校准）

**成本按三关分开核算**——递进式验收的价值本身就体现在成本曲线上，因此不能只报一个总额。

| 指标 | 目标 | 说明 |
| :--- | :--- | :--- |
| 第一关 单批 12 条脚本耗时 | 待实测 | 应显著低于出图与出片，否则递进失去意义 |
| 第一关 单条脚本成本 | 待实测 | 纯文本，应接近于零 |
| 第二关 单条分镜图成本 | 待实测 | 按分镜数 × 单价计 |
| 第三关 单条成片成本 | 待实测 | 需低于商家心理价位（个位数人民币） |

| **三关成本比** | 待实测 | 预期脚本 : 图 : 片 呈量级递增，是递进验收成立的前提 |

**编排与生产分层**：配方生成走官方 `dsh-workflow` 脚本层（`agent()` 全新上下文子代理）；画面生产走 `omnimux-workflow` 画布层。画布节点当前仅支持媒体类（`material:import` / `material:generate`），**不新增 LLM 节点**。

**三关的成本意义**：S1 几乎不花算力，却是决定后续成败的一关。若 S1 的脚本评分长期达不到 3.5，问题出在池子与配方——**不应带着问题进入 S2 出图**。这正是递进验收要防的事。

### D1 命名变更说明

上游设计方案（`design.md` v0.1）中我推荐的是 `omnimux-variants`（变量库）。本版改为 **`omnimux-recipes`（配方库）**，原因：老板明确了产品主线是「**模板适配** → 基于模板生成 → 固化模板」，**模板与配方是主体，变量是手段**。"配方"同时天然承载"可固化、可复用"的语义，与两阶段闭环吻合。

### D7 待确认：首批垂类建议

按模板池覆盖厚度建议（需老板拍板）：

| 候选垂类 | 池子依据 | 建议 |
| :--- | :--- | :--- |

### D8 待确认：画面形态是否参与首期抽样 ⚠️

**与 D2 存在实现层冲突，需拍板后统一。**

D2 已定「首批仅开人设 × Hook，画面层冻结」，但 S0 落地的脚本把画面形态也纳入了抽样（三轴各自抽样）。这不是实现失误，而是**池子容量暴露出的硬约束**——两者必须二选一：

| 选项 | 单角色上限 | 符合 D2？ | 代价 |
| :--- | :--- | :--- | :--- |
| **A. 冻结画面形态**（首期只测人设 × Hook） | **15 条** | ✅ 符合 | 批次内画面形态单一 |
| B. 保持现状（形态也参与抽样） | 6 条 | ❌ 违背，实际开了三个因子 | 12 条样本拆不开三个因子的效应 |

**建议 A**，两条理由：

1. **与 D2 一致**：只让要测的因子变化，是正交实验的基本纪律。三个因子同时变，数据回来无法归因。
2. **解除容量瓶颈**：当前九个垂类全部卡在 6 条，唯一原因就是画面形态池只有 6 个。冻结后上限立刻升到 15 条（受 Hook 池限制）。

拍板后需同步修改：`batch-shoot.v0.js.txt` 的抽样逻辑、`pools/format.json` 的 role 划分、以及 `scripts/workflows/OMNIMUX-PROMPT.md` 的上限说明。

## 十二、边界扩展声明（需明确授权）

按 `AGENTS.md` 的 MVP 边界条款，当前授权范围是**爆款视频复刻**（发现 → 解构 → 复刻），"社媒账号矩阵、通用创意画布、自动化发布排期、独立运营分析"为默认范围外。本 PRD 属于**边界扩展**，按四部分披露：

1. **跨越的边界**
   从「单条爆款复刻」扩展为「批量变量化生产 + 模板适配 + 模板固化」。新增了模板池适配、正交配方引擎、批次血缘三个能力模块。

2. **最小实现范围**
   仅新增一个领域插件（变量池 + 配方引擎 + 任务状态机 + 血缘）。生产走 hub seam，模板固化复用 `workflow` 的 `TemplateStore`，商品与资产复用现有插件，**不改动 hub、不改动官方组件、不新增第二个 router**。

3. **成本与风险**
   - 算力成本随批量线性上升（本版以「12 条/批 + Sample Gate + 并发上限」约束）
   - 归因闭环本版不做，所以**"固化模板"在 S5 之前只能靠人工判断**
   - 递进验收把交付阶段从 5 期拉到 7 期，**每期都有一道人工验收门**，需老板或运营实际投入打分时间
   - 存量素材存在被平台判定同质化的风险，靠「迁移骨架不搬素材 + 三重防线」控制

4. **避免扩张的替代方案**
   不新增插件，改为在 `omnimux-inspiration` 内加一个「变量配方」子视图。成本更低，但会把"复刻"与"批量生产"两种语义混在同一插件内，且难以承载批次状态机与模板固化，长期维护成本更高。

**结论**：PRD 成立。S0 已完成，待 §十一 D7、D8 拍板后进入 S1。
