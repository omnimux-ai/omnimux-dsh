# 模型接口准据：渠道官方 API 文档

模型支持哪些模式、接收哪些输入，始终以实际使用渠道的官方 API 文档为准。模型调研、接入、参数面板与契约验收不发起真实模型 API 请求，不用生成结果或报错反推接口规范。

## 1. 主要渠道与来源

| 渠道 | 官网 | 官方 API 文档入口 |
|---|---|---|
| EvoLink | [evolink.ai](https://evolink.ai/) | [API 文档](https://evolink.ai/docs) |
| APIMart | [apimart.ai](https://apimart.ai/) | [API 文档](https://docs.apimart.ai/) |

以上是项目主要渠道，由用户指定；文档入口于 2026-09-05 核对。入口只用于发现页面，具体约束必须引用该渠道对应模型、版本、端点的参数页或官方 schema。记录最终页面 URL、核对日期及适用条件。

2026-09-05 阶段一的七款视频模型批次曾固定使用 APIMart，不做自动切换；这不是当前全产品的渠道路线。现行产品方向见[产品定位](product-positioning.md)，内部同组候选规则见[中枢合同](hub.md#角色创作与内部路由要求)，不能跨渠道借用字段与限制。产品模型 ID 与 APIMart `model` 字段的精确映射见 [阶段一范围规格](../specs/2026-09-05-video-phase-one-scope.md)。EvoLink 只在 [独立渠道记录](../references/evolink-video-channel.md) 中维护，本批不得引用其字段、限制或价格补 APIMart 的缺项。

- 同名模型在不同渠道分别建账。不得把 EvoLink 的字段、数量或格式限制套到 APIMart，反之亦然。
- 渠道文档是该渠道接入规范的准据；原厂资料、营销首页、模型名后缀、仓内旧摘要、测试结果都不能覆盖它。
- 模型或路由尚未确认属于哪个渠道时，明确标为待确认，不能按名称猜渠道。
- 文档缺项或相互矛盾时记录未知项、冲突页面和适用版本；继续查该渠道官方文档，不试探字段、不递增输入找拒绝点、不自行取更严值冒充官方限制。

## 2. 模式与输入盘点

按「渠道 + 模型 ID/版本 + 端点 + 模式」记录：

| 内容 | 必须保留的信息 |
|---|---|
| 模式 | 文档中的模式名、触发条件、与内部 operation 的对应关系 |
| 输入 | 字段名、类型、必填条件、角色、数量范围、互斥与组合规则 |
| 媒体 | MIME/格式、尺寸、体积、时长及分别适用的输入或输出 |
| 参数 | 枚举、范围、默认值、分辨率/时长等联动条件 |
| 来源 | 精确官方 URL、核对日期、明确支持/不支持/未说明 |
| 实现 | mapper、槽位、校验和 UI 是否覆盖；未覆盖项单列为实现缺口 |

必须检查首尾帧生视频、全能参考生视频等文档模式，不能把已测试过的模式当成完整清单。全能参考可能涉及图像、视频、音频及其角色组合，不能直接等同于多图参考；实际支持范围仍逐渠道、逐模型以文档为准。现有 registry 缺少对应表达时记录实现缺口，不把模式压成错误的旧 operation，也不在文档修订中自动新增实现。

文档上限直接作为接口约束依据。测过一张或两张图只说明历史样本，不能推导最大数量。确有产品自身限制时，须单列其适用范围和理由，不得写成渠道 API 限制。

## 3. 验证边界

1. 阅读公开文档并核对 schema、字段映射与参数定义。
2. 使用本地 fixture、mock 和隔离测试验证请求构造、边界校验、错误提示及响应解析；不调用真实模型端点、上传素材、轮询任务或查询在线模型列表作为补证。
3. UI 改动仍完成规定的真实浏览器验收，生成动作由离线夹具覆盖；真实页面验收不授权真实模型请求。
4. 不设置「每模式一次真实最小请求」「测不过不上架」或逐步递增输入的验收门槛；旧探测脚本和预算不是继续发请求的授权。

## 4. 三类事实分别记录

| 事实 | 证明方式 | 不代表什么 |
|---|---|---|
| 文档支持 | 适用渠道的官方接口页/schema | 本产品已接好、曾真实生成成功 |
| 实现覆盖 | 代码核对、离线测试、必要的浏览器交互证据 | 渠道当前可用性或真实输出质量 |
| 历史真实执行 | 原有请求时间、状态、输出和来源记录 | 完整模式清单、数量上限或文档支持范围 |

历史证据原样保留，标清渠道与日期；不能把未测试写成不支持，不能把离线测试或 stub 写成真实生成。既有 `mode: "live"` 的诚实声明要求仍有效，它不构成必须发请求的要求。

## 5. 与当前目录实现的关系

`computeOperationListed` 将渠道文档确认与实现就绪作为目录准入条件，并继续检查兼容 profile 与 gate；`execution.live` 只保留历史真实执行事实，不再是上架前提。这一拆分不授权真实请求，也不能把离线 fixture 标成真实执行。

后续接入应依据官方文档和离线实现证据调整目录准入表达，将实现覆盖与历史真实执行分开。不得伪造 `execution.live`、批量标绿或仅改文档宣称模式已可用；保留 schema、mapper、profile 相容和提交前校验要求。

本合同取代旧方案中「真实请求补证、探测输入上限、按实测样本收窄官方能力」的方法要求。旧证据和阶段快照只作历史记录；当前执行规则统一指向本文。
