# MVP scope: viral video replication

`AGENTS.md` carries the always-on summary of this contract. This file holds the complete admission and consent rules. Agents MUST NOT edit this contract or the `AGENTS.md` MVP section to bypass user confirmation.

## 1. Target

Deliver the viral video replication MVP across discovery, deconstruction, and replication. Progress is measured by verified loops that produce usable, playable, exportable video deliverables aligned with the user's rewrite intent.

| Step | Activity | Verification evidence |
| --- | --- | --- |
| Discovery | Finding or selecting reference video and input samples | Verified reference sample |
| Deconstruction | Extracting structure, pacing, hooks, and shot expression | Structured deconstruction output |
| Replication | Producing, editing, and exporting a reproduction aligned with the goal | Playable, exportable video deliverable |

- Completing the first end-to-end loop is a progress milestone, not an authority release.
- Repeated exports of the same deliverable do not increment the loop count.
- Never substitute vanity metrics (views, revenue) or build external analytics platforms.

## 2. Admission

- Excluded by default (separate confirmation required): social account matrices, generic creative canvases, automated publishing schedules, standalone operations analytics, and speculative whole-repo refactorings.
- Evaluate a change by business intent and active task authorization, never by directory location or speculative future efficiency.
- Supporting work (asset pipelines, model routing, clip adaptation, local UX polish, bug fixes, unit tests) is admitted only when it directly serves an authorized loop, addresses a concrete gap, stays minimal, and introduces no independent capability.

## 3. Boundary pause and consent

- Pause unapproved out-of-scope or ambiguous implementation, configuration, activation, or architectural changes before acting; never build first and report later. Safe read-only investigation and independent authorized tasks may proceed.
- When requesting confirmation, state: (1) the exact boundary crossed, (2) the minimal implementation scope, (3) costs and risks, (4) alternatives that avoid expansion.
- Proceed only on informed, explicit consent. Silence, vague phrasing ("handle it"), pre-existing code, tool availability, or delegation do not confer authority.
- Carry a specific authorization across turns without re-asking; re-confirm only when scope or risk expands. An initial request that names and approves an out-of-scope expansion satisfies confirmation. One-time exceptions never change the MVP boundary.

## 4. Persistence

- The boundary governs until the user explicitly updates it. Completing the first loop or toggling full/MVP switches does not lift it.
- This contract does not authorize deleting, disabling, or activating existing code.
- All product boundaries in `AGENTS.md` remain. Account, credential, publication, and production writes keep explicit authorization; real-money transactions stay human-only. This is a behavioral agreement, not an external approval gate.
