## 0. 决策问题

commit `1ba8981` 刚把 `social-engagement-team`（社媒互动增长专家团）从 5 人扩到 7 人：
在增长运营五人组（格罗斯 Growth / 柏特 Bot / 瑞普 Reply / 麦恩 Mine / 沃奇 Watch）之上，
新增 2 名内容生成子代理（可可 Copy 文案 / 维森 Vision 视觉分镜），并随包内化 8 款 Tier1
创作类技能（ad-creative、social-caption、content-strategy、dynamic-poster、
character-scene-storyboard、cinematic-motion-language、clip-export、ecommerce-image）。

本 memo 回答：**社媒内容创作**与**社媒互动增长/矩阵运营**，应该
A) 合在一个大专家团（All-in-One 覆盖社媒全生命周期），
B) 拆成两个独立专家团，还是
C) 组织拆分 + 目录组合入口？

从产品定位、用户心智与场景旅程、Token 经济学与推理稳定性、商业化包装与出厂分发四个维度给出结论与落地重构建议。

## 2. 四维深度研讨

### 2.1 产品定位：内容创作是横切能力层，增长是纵向业务域

**核心论断：内容创作在 OmniMux 里不是「社媒的附属环节」，而是一个横切能力层；互动增长才是纵向业务域。把横切能力焊进一个纵向团队 = 架构错位。**

1. **技能层的证据已经证明跨域性（E3）**：8 款 Tier1 技能里，`clip-export` 的宿主是剪辑工坊（omnimux-clip / 剪映导出），`ecommerce-image` 的宿主是电商图（omnimux-products 域）——它们被随包捆绑却无人绑定，恰好说明这批技能服务的下游不止社媒。若把全部 8 款焊死在社媒增长团队内，等于宣布「电商图、剪辑导出只属于社媒增长」，与插件域边界（E10）直接冲突。

2. **JTBD 分离**：
   - 增长运营团队的产出是**策略与情报**（策略文档、评论矩阵、线索清单、舆情预警）——信息，用完即焚，不可复用；
   - 内容团队的产出是**资产**（文案、分镜表、海报版式、运镜提示词）——进入资产库（omnimux-assets 的 `real_path` 零拷贝）后可被多次再加工。
   - 两种产出分别对接资产库与报告流，生命周期完全不同。

3. **行业先例即常识**：广告公司里创意部与媒介购买/增长运营部从来是**两个组织**——KPI（作品质量 vs 增长结果）、工种（审美与叙事 vs 数据与风控）、方法论（灵感驱动 vs 漏斗驱动）完全不同。AI 团队层照搬这一分工，不是平庸，是跟成熟心智对齐。

4. **定位表述**：
   - 社媒内容创作专家团 = 「把想法变成资产」的上游产线（创作工作室）；
   - 社媒矩阵增长运营专家团 = 「让资产产生增长」的下游运管（增长指挥部）。
   - 产线服务多个下游（社媒、电商、短剧、出海），运管只服务自己的域。

### 2.2 用户心智与场景旅程：两个触发词、两条旅程、两种信任

**核心论断：合体团队的「增长」人设锚点会成为创作用户的首英里摩擦；轻量任务不该付「组建团队」的心智税。**

1. **触发词召回**：用户的提问词是「写一条小红书文案 / 拆个分镜」vs「帮我涨互动 / 找购买意向用户」。目录搜索、输入框联想（283 技能 0-token 联想，E1）按词匹配；团队名「社媒**互动增长**专家团」与创作词天然不匹配 → 召回错位、心智迷惑。

2. **旅程对照**：

   | | 创作旅程 | 增长旅程 |
   |---|---|---|
   | 入口意图 | 要一篇文案/一份分镜 | 要一套增长策略/监控体系 |
   | 主步骤 | brief → 文案 → 分镜 → 资产入库 → 发布 | 诊断 → 策略 → 自动化/评论/信号/监控 → 复盘 |
   | 主要落点 | omnimux-assets / inspiration / clip / publish | omnimux-accounts / publish / analytics |
   | 频率/承诺 | 高频、轻承诺、可试错 | 低频、重决策、需信任 |
   | 信任锚点 | 信我的审美与文笔 | 信我的操盘与风控 |

   合体后创作用户必须先穿过 SOP Phase 1 的**增长诊断**（账号状况、增长目标、安全边界）——对只要一条文案的用户是负价值首英里。

3. **心智税**：7 人大名单 + 六阶段 SOP + TeamCreate 仪式，对「就要一条文案」的轻量用户是劝退面。存在 8F 风险（功能过剩 Feature-itis → 心智负担）。轻量先例 E9（content-creation-team SKILL 三步轻形态）证明内容域用户偏好浅入口。

4. **命名与品牌稀释**：一个团队同时宣称「增长策略旗舰」与「内容工作室」，两个品牌资产互相稀释；拆分后每个团队名本身就是定位宣言。

### 2.3 Token 经济学与推理稳定性：交棒应该发生在状态层，而不是 prompt 层

**核心论断：合体方案把「必然发生的跨域交棒」从插件状态层（廉价、可追溯、可重放）搬进 prompt 层（昂贵、易漂移、难归因）。**

1. **定义成本（Definition Cost）随队膨胀**：7 人团队提示词 1,082 行（E2）。lead 的 274 行里塞着 6 名成员能力清单 + 六阶段 SOP + 直调路由表——每次会话常驻；每次 spawn 成员又要把成员 prompt + 绑定技能全文装载。

2. **单任务成本对比（定性估算）**：
   - 一个「写条文案」任务：合体路线 = TeamCreate + 主理人常驻（含全部增长成员清单）+ 可可装载 3 技能 751 行；独立内容团队路线 = 更薄的 lead + 同一份技能装载。合体路线多出约 40–60% 的固定上下文与更多「不该出现」的上下文（增长成员、舆情框架）。
   - 维森侧更重：3 技能 1,137 行（E3）。只要团队合体，视觉能力清单就常驻在增长任务上下文里——纯浪费。

3. **串行链路是稳定性黑洞**：「可可 → 主理人中转 → 维森」先文后视（E5），两次独立推理 + 中转摘要 = 更高 Token 消耗 + 内容漂移 + 质量归因模糊。LLM 在「长清单 + 多角色 + 多阶段状态机」下的指令遵循衰减与越界率上升是普遍观测（TeamCreate + 150 turns 上限 + 并行 Phase 4 叠加串行 Phase 5 = 状态空间最大的形态）。

4. **反方观点与回应**：端到端场景（从 0 出一条「带内容的增长方案」）合体可省一次用户侧上下文转述。回应：产品 brief 应沉淀在 **omnimux-products 产品卡 / omnimux-assets 资产库 / inspiration 灵感源**（分布式声明），两个团队各自读取即可，交棒成本不仅归零且更可靠——这正是「分布式声明 + 聚合」的意图，合体反而是与它背道而驰的单体反模式。

### 2.4 商业化包装与出厂分发：货架已拥挤，超级 SKU 会自相残杀

**核心论断：拆分 + 技能中台 + 目录组合，是唯一能同时拿到「清晰 SKU 树」与「一个入口体验」的形态。**

1. **目录货架证据（E7）**：17 个专家团里内容/增长/营销域已有 ≥8 个重叠 SKU（内容创作专家团、全域内容分发专家团、内容变现商业化专家团、营销战役与内容、营销增长专家团、SEO 内容营销团队、AI视频创作团队、视频解剖专家团）。social-engagement-team 再长出内容成员 = 与货架上「内容创作专家团」直接打架。合体 = 一个团队同时和 3+ 个 SKU 竞争，谁都赢不了。

2. **SKU 逻辑**：内容 SKU（高频轻决策、易试用、可订阅）与运营 SKU（低频重决策、需信任、可顾问化/定制化）定价模型完全不同。合体只能定一个价——要么贱卖策略价值，要么吓退文案用户。

3. **分类自伤（E8）**：plugin.json 说自己是增长营销（05-MarketingGrowth），目录把它摆在平台运营（exp-platform）；合体后这个问题无解（内容创作？平台运营？增长营销？三个货架位都占不全）。

4. **出厂分发红利**：JIT 静默热装载 + 目录点卡召唤（未安装先装进 skills 目录、`/技能名` 手势注入、空白会话切专家预设，E1）意味着**分发成本已近零**。拆开完全不损害开箱体验：
   - 出厂默认 = **增长闭环 SKU**（社媒矩阵增长运营专家团 + omnimux-accounts + omnimux-publish）——这是账号持有者的第一刚需；
   - 内容专家团进目录按需召唤，8 款创作技能继续 bundled（断网开箱即用承诺保留）。
5. **组合入口**：目录 `featured` 增加「社媒增长全家桶」组合卡（引用两个团队，零耦合），商业上做 bundle 定价、体验上给「一个入口」——C 方案同时拿到 B 的清晰与 A 的聚合感。

## 3. 三方案对照

| 维度 | A 合体（现状+扩张） | B 拆两个团队 | C 拆分 + 目录组合入口 |
|---|---|---|---|
| 产品定位 | 低：JTBD 混杂、与插件域边界冲突 | 高：内容=产线/增长=运管 | 高：物理拆分，聚合只在目录层 |
| 用户心智 | 中：单一入口但首英里摩擦、触发词错位 | 高：词即入口、两种信任锚点 | 高：组合入口 + 直达车道兼顾 |
| Token 经济学 | 差：1,082 行定义常驻 + 串行交棒 | 好：按车道装载、上下文更薄 | 好：同 B |
| 推理稳定性 | 差：状态空间最大、质量归因模糊 | 好：域内状态机短而清晰 | 好：同 B |
| 商业化 | 差：与 ≥3 个既有 SKU 自相残杀、只能定一个价 | 中：SKU 清晰但缺聚合感 | 好：双 SKU + bundle 定价 |
| 架构契合 | 违背：单体反模式 | 契合 | 最契合（分布式声明 + 目录聚合） |
| 迁移成本 | 0（但持续付错付） | 低：git mv 两个成员 + lead 瘦身 | 中：同 B + 组合卡 UI（二期） |

**结论：选 C 为终态，落地先走 B。** 组织上必须拆分；「一个入口」的体验用目录组合卡与插件状态接力实现，而不是把两个团队焊进一个 prompt。

## 5. 落地重构建议（文件级）

### Phase 1：物理拆分（对应一次小 PR，复用 1ba8981 全部资产）

1. 新建 `catalog/experts/social-content-team/`：
   - `agents/social-content-team-lead.md`：内容主理人（审美/平台语境/资产交付，管辖可可+维森，预留剪辑、电商图坑位）；
   - `agents/content-copywriter.md`、`agents/visual-director.md`：从 growth 团队 **git mv** 迁出，正文「你是社媒互动增长专家团的…」改为「你是社媒内容创作专家团的…」，其余保留（隔离铁律、技能绑定照旧）；
   - `settings.json`、`README.md`、`.codebuddy-plugin/plugin.json`（expertType=team；memberAgents=[lead, copywriter, visual-director]；指向 catalog/skills 的 6 款技能**引用而不复制**——技能留在中台一层）。
2. 收缩 `social-engagement-team`：
   - plugin.json 的 memberAgents 删 2 人，skills 保持 `social-engagement-ops`；
   - `social-engagement-team-lead.md`：删 Phase 5、删可可/维森能力清单与路由行，maxTurns 150 → 100；README 回 5 人表述；
   - 补齐 growth lead 一条接缝：「从 omnimux-assets / 发布台账读取已有内容作为互动弹药上下文」（读，不内建生产）。
3. 技能归位声明（README/meta 标注，不搬文件）：
   - `clip-export` → omnimux-clip 域（剪辑工坊导出能力）；
   - `ecommerce-image` → omnimux-products / 电商域；
   - `content-strategy` → 中台共享（选题服务于增长也服务于创作）。

### Phase 2：目录与出厂

4. index.json 修正分类：social-engagement-team 与 plugin.json 对齐（建议 `exp-growth`，与营销增长专家团同区）；内容团队落 `exp-writing` / `exp-video`。
5. `featured` 组合卡「社媒增长全家桶」（引用 content + growth 两个团队 id，零耦合），一期只做文案级标注，二期再给引导式安装流。

### Phase 3：接力契约（先立约定，后落代码）

6. 跨团交棒约定：产品卡（products）→ 内容团队出稿 → assets 入库 → publish 发布台账 → 增长团队复盘喂选题。状态存在各插件域 store，聚合发生在工作流画布（omnimux-workflow）或用户会话——**不新增第二个「中枢」**（术语遵守 AGENTS.md：中枢专指 omnimux 执行中枢）。

### 度量与验证（拆后 4 周）

- 单任务 Token 成本较拆前基线 **-30% 目标**（同任务集对比）；
- 简单任务不落 SOP 的**直调率 ≥ 70%**；内容任务从召唤到产出首轮 ≤ 2 次往返；
- 两个 SKU 的安装率/召回率、组合卡转化；跨 SKU 接力掉话率 < 10%；
- 内容团队 SLO：文案/分镜一次过审率、资产入库率（进 omnimux-assets 的比例）。

## 6. 风险与反方意见回应

| 风险 | 回应 |
