# ADR 2026-10-01: 媒体任务生命周期统一与 Hub 任务账本权威

## 状态
Accepted

## 背景与问题陈述
在 OmniMux 创作画布中，当用户使用官方模型（如视频 `minimax-h3` 首帧生成）或本地 CLI 语音模型生成时，节点频繁抛出错误：
`[omnimux:omnimux-unconfigured] 本机助手只承接文字，图片、视频和音频需要配置媒体生成提供商或改用官方`。

经过深入技术调查，根本原因在于**媒体生成两阶段（提交与等待）上下文丢失与重复准入判定**：
1. **两阶段上下文割裂**：首次 `submit` 阶段携带完整模型 ID 与参数，通过了准入并在上游成功创建任务返回 `taskId`；第二阶段取结果时，画布网关 `awaitTask` 仅传 `{ taskId, dest }`，丢弃了原始模型、提供商和渠道信息。
2. **多路重复检查与误拦**：虽然 `mountMedia` 依据默认官方模型放行并透传了系统凭据，但在底层的 `executeOmnimuxMedia` 执行器中，由于缺少 `input.model`，在进入 `taskId` 轮询分支（474–482行）之前，先行触发了 Agent 对话模式检查（265–271行），将该轮询等待请求错误地当成“未配置媒体生成提供商的本机助手请求”予以阻断。
3. **缺乏统一持久化任务权威**：Hub 内部未持久化任务与实际路由的绑定关系。当特定模型具有特殊任务路径（例如 `index-tts` 实际走视频任务路径）时，上下文缺失会导致路由漂移。
4. **工作流异常清除机制过激与计费风险**：工作流网关执行器 `materialGatewayExecutor.ts` 在 `catch` 中无条件执行 `ctx.clearUpstreamTask()`，导致任何网络抖动或本地鉴权异常直接丢失上游任务引用；且 `upstreamReconcile.ts` 将 404/未知请求归类为可重新提交（`not-reconcilable`），在缺乏上游任务状态确认时极易造成重复提交、重复计费。

## 决策方案
我们决定采用 **方案 A：由 Hub 持有窄范围、持久化的媒体任务账本，统一返回不透明 `taskRef`**。

具体契约与架构如下：
1. **Hub 任务账本为唯一传输权威**：
   - 存储路径：当前 Host Profile 下的 `$DSH_HOME/omnimux/media-tasks/`（目录权限 `0700`，单文件 `0600`，采用原子写入）。
   - 记录上游任务传输身份、提交时锁定的实际模型与端点、绑定的凭据引用、原始提交时间、轮询路径与拉取缓存。
   - 仅负责传输与任务生命周期，不涉及画布拓扑或业务项目资产。
2. **二元正交职责分离**：
   - `submitMediaTask(capability, input, context)`：唯一负责新生成准入校验、参数收敛、模型路由解析与上游提交，返回持久化 `taskRef`。
   - `collectMediaTask(taskRef, input, context)`：唯一负责按账本记录的原路由查询状态、下载产物、校验媒体有效性并交付目标路径。**严格跳过新生成模式准入校验，彻底消除 `omnimux-unconfigured` 误拦**。
3. **工作流与画布解耦**：
   - 画布与工作流仅持有 `taskRef` 句柄，不复制、不推导底层模型路由。
   - 废除对易失内存任务表的不可靠依赖，确保跨进程重启后可通过 `taskRef` 准确定位原任务。
4. **受阻保护与安全恢复机制**：
   - 遇到可恢复异常（如 401 凭据失效、网络超时、下载校验错误）时，严禁无条件清除 `upstreamTask` 引用；
   - 执行器进入受阻暂停态，保留当前任务句柄与断点；用户更新凭据或恢复网络后，通过顶栏现有“恢复执行”按钮原地继续收取；
   - 上游明确终态失败、404/410 或未知任务严格 Fail-Closed，绝不自动重新发起生成提交。
5. **确定性幂等入库**：
   - 产物先写入 Hub 管理的临时缓存并完成非空与媒体有效性校验；
   - 工作流依据 `executionId + nodeId + attemptIndex` 派生的确定性交付键与文件名写入项目 artifacts，并原子更新资产账本 `assets.json`。

## 后果与权衡
- **积极影响**：
  - 彻底终结画布官方视频/音频任务在轮询阶段被误杀为“本机助手只承接文字”的问题；
  - 杜绝因鉴权失效或网络闪断导致的重复扣费与任务丢失；
  - 跨进程重启后具备稳定可靠的断点续查能力。
- **消极影响 / 限制**：
  - 必须维护文件级任务账本的写入与读取开销；
  - 历史无 `taskRef` 且在上游无法核实的孤儿任务将被严格归类为不可恢复终态，需用户明确重新发起生成。
