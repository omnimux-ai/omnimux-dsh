## 脚本

两个脚本都用 headless Chrome + CDP 驱动**真实浏览器**跑原型页面，不是静态模拟。需要本机装了 Google Chrome。

```bash
cd docs/evidence/account-monitor-v2
node verify.mjs > run.log 2>&1; echo "REAL_EXIT=$?"      # v2.0：42 项断言，17 张截图
node verify-v21.mjs > run-v21.log 2>&1; echo "REAL_EXIT=$?"  # v2.1：43 项断言，截图 14–20
```

两个脚本都会把结果写进同目录的 `results*.json`，并把截图写进当前目录。截图是 24 MB 量级，没有入库；需要复现时本地跑脚本即可重新生成。

`verify.mjs` 断言的是 v2.0 口径（含平台角标、底部状态条等）。**v2.1 改掉了这些元素，所以 `verify.mjs` 已经过期**，只保留作为历史记录；当前口径看 `verify-v21.mjs`。

## v2.1 断言覆盖

43 项，重点是这些容易被「看起来对」蒙过去的地方：

- 瀑布流按最短列放置：**独立复算**每张卡的列索引，再和页面实际渲染的坐标逐张比对，不是读页面自己的算法结论
- 列数边界：Feed 容器 1164 → 5 列、1163 → 4 列、928 → 4 列、927 → 3 列；列宽等分且 ≥ 220px
- DOM 顺序等于排序顺序（默认排序与增速排序各测一遍）
- 悬停与「标为已处理」之后所有卡片位置不变
- 媒体比例 9:16 / 16:9 / 4:5 / 1:1；截断行数 1 / 2 / 1 / 8 / 3
- 默认态逐张卡扫描可见文本，确认只暴露媒体、胶囊、标题或正文
- 已处理卡：媒体 `grayscale(1)` + `opacity 0.45`、胶囊中性化、正文降级；整卡 `opacity` 仍为 1
- 对比度用**截图像素**采样真实合成底色后按 WCAG 计算，亮暗两套主题都测
- 亮色主题下已处理媒体的中心亮度 ≥ 0.15（专门挡住「压成黑块、看起来像加载失败」）
- 悬停层上沿 20px 渐隐带、无顶边描边与顶部圆角

## 人眼复检

自动化断言测不到构图破败与视觉平衡，所以每轮都另外看了截图。这一轮人眼复检发现并退回修复的问题：

1. 已处理卡的媒体被 `brightness(0.6)` 压成纯黑块，看起来像加载失败 → 改为只降不透明度，向卡底淡出
2. 文本卡悬停层顶边硬切正文第 2 行，露出半行字 → 改为上沿 20px 渐隐
3. 亮色主题下文本卡中性胶囊文字对比度只有 2.4:1 → 改用 `label-secondary`
4. 详情弹窗「平台」栏同时显示平台图标和平台名，同义重复 → 只留文字

## 已知跟踪项（非阻塞）

1. 亮色主题下已处理卡的媒体胶囊没有亮度下限，实测 4.86:1 只比 AA 线高 8%；若真实封面接近纯白会掉到约 2.4:1。建议与真实缩略图接入同批处理。
2. 原型媒体是 CSS 渐变占位而非真实照片，「不像加载失败」目前只在色调层可验，纹理层要等真实缩略图接入后复检。
